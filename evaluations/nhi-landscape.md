## 1. What h2a already exports (the interop surface to feed out)

P3 is about pushing h2a's **existing** artifacts to an external system (or pulling inventory in). h2a introduces no new artifact for this — the candidate payloads already exist in `@sentropic/h2a` (`packages/h2a/src/nhi.ts`):

- **Posture report** (`nhi report`, DEC-087) — `H2ANhiPostureReport`: `{ generatedAt, summary, findings[] }`, where each `finding` is `{ risk (NHI1/4/5/7/9), title, csf, severity, count, detail, subjects[] }`. A deterministic OWASP-NHI / NIST-CSF classification of the registry. No secrets, no PEMs (keys appear only as `nhiKeyFingerprint`, a 12-char non-reversible hash).
- **Signed attestation envelope** (`nhi attest`, DEC-088) — a plain h2a `event` envelope (`H2AEnvelope`) whose body is `{ kind: "nhi-attestation", report }`, signed with ed25519 via `signEnvelope`; verifiable by anyone holding the signer's public key with `verifyEnvelopeSignature`. Carries `{ protocol, version, createdAt, actor:{instance,role,scope}, body, signatures[] }`. This is the evidence-grade payload.
- **Inventory** (`nhi inventory`, DEC-090) — `H2ANhiInventory`: `{ generatedAt, totals, instances[] }`; per instance `{ id, role, offboarded, keys[{fingerprint, addedAt, ageDays, longLived, sharedWith[]}], subagents[{id,status,capabilities,bounded}] }`. A per-identity estate view (reuse, key-age, offboard state).

These three are the things P3 would map onto an external system's ingestion API. Keep this in mind reading the table: "h2a-interop relevance" answers *which of these three a given target could consume, and in which direction*.

## 2. Standards / frameworks

### OWASP Non-Human Identities Top 10 (2025)
The concrete, actionable de-facto checklist. An OWASP **Documentation / Incubator** project at version **2025**, sponsored by Astrix Security with contributors from Torch, Snyk, Orca and others; endorsed by the Cloud Security Alliance ([owasp.org project page](https://owasp.org/www-project-non-human-identities-top-10/); [2025 list](https://owasp.org/www-project-non-human-identities-top-10/2025/top-10-2025/); [CSA endorsement](https://cloudsecurityalliance.org/blog/2025/06/30/introducing-the-owasp-nhi-top-10-standardizing-non-human-identity-security)). The ten risks (NHI1 Improper Offboarding · NHI2 Secret Leakage · NHI3 Vulnerable Third-Party NHI · NHI4 Insecure Authentication · NHI5 Overprivileged NHI · NHI6 Insecure Cloud Deployment Configurations · NHI7 Long-Lived Secrets · NHI8 Environment Isolation · NHI9 NHI Reuse · NHI10 Human Use of NHI) are exactly the taxonomy h2a's `nhi report` classifies against (it derives the subset NHI1/4/5/7/9 from its own registry). **Relation to h2a primitives**: this is the vocabulary of the posture report — it is the *content standard* for what h2a exports, not a transport. Interop value: a posture report is already "OWASP-NHI shaped", so any target that speaks OWASP-NHI risk IDs can ingest it without translation.

### CSA (Cloud Security Alliance)
Endorses the OWASP NHI Top 10 (above) and is active on NHI via its summits and the **SaaS Security Capability Framework (SSCF)**, released 2025-09-24, which defines baseline SaaS-vendor controls including non-human-identity governance, strong auth, entitlements and just-in-time access ([CSA SSCF / Help Net Security](https://www.helpnetsecurity.com/2025/09/25/csa-saas-security-capability-framework-sscf/); [CSA blog](https://cloudsecurityalliance.org/blog/2025/09/19/identity-security-cloud-s-weakest-link-in-2025)). **Relation to h2a**: framing/governance-level, no transport h2a would export to directly. (Note: I did not locate a single dedicated CSA "NHI standard document" with a stable spec URL beyond the OWASP endorsement and SSCF — flagging this as a possible gap rather than asserting one exists.)

### NIST — SP 800-207 (Zero Trust) and CSF 2.0
As established in [nhi.md](./nhi.md): **no dedicated NIST NHI standard exists** (as of 2026-05). SP 800-207 *Zero Trust Architecture* treats **Non-Person Entities (NPE)** as an authentication/audit concern but leaves NPE governance to the implementer — it is not a prescriptive NHI spec. **CSF 2.0** (govern/identify/protect/detect/respond/recover) is the framework an NHI program maps to, and is exactly the `csf` field each h2a finding already carries. **Relation to h2a**: framing-level alignment; not an export target. (Sourcing for these two is carried in nhi.md; not re-fetched here.)

### SPIFFE / SPIRE (CNCF)
**SPIFFE** is a set of open specs for issuing identity to workloads across heterogeneous environments; the credential is the **SVID** (SPIFFE Verifiable Identity Document), an X.509 cert or JWT a workload presents to prove identity. **SPIRE** is the reference implementation (SPIRE Server + Agents) issuing/rotating short-lived SVIDs via a local **Workload API** (Unix-domain-socket); workloads need no pre-shared secret because **node + workload attestation** roots identity in platform/OS evidence ([SPIFFE concepts](https://spiffe.io/docs/latest/spiffe-about/spiffe-concepts/); [SPIRE concepts](https://spiffe.io/docs/latest/spire-about/spire-concepts/); [Working with SVIDs](https://spiffe.io/docs/latest/deploying/svids/)). **SPIFFE Federation** exchanges **trust bundles** (the trust domain's issuer public keys/certs) between trust domains over an HTTPS **bundle endpoint**, so SVIDs minted in one domain can be verified in another; trust bundles are the only artifacts exchanged ([SPIFFE Federation spec](https://spiffe.io/docs/latest/spiffe-specs/spiffe_federation/); [standards/SPIFFE_Federation.md](https://github.com/spiffe/spiffe/blob/main/standards/SPIFFE_Federation.md)). **Relation to h2a primitives** (strong): this is the closest standard to what h2a *does*. h2a's ed25519 signed envelope ≈ a self-issued verifiable credential; h2a's `keyring` (active public keys, rotation add→overlap→revoke) ≈ a trust bundle that changes over time; verify-on-receipt ≈ SVID verification against a bundle. The natural interop is **trust-anchor exchange**: publish h2a's active public keys the way a SPIFFE bundle endpoint publishes issuer keys, and/or map an h2a instance id to a SPIFFE ID, so a SPIFFE-aware verifier can validate an h2a attestation envelope. h2a is *not* a SPIRE replacement (no node/workload attestation, no SVID minting), but it is bundle-/credential-shaped.

### IETF WIMSE (Workload Identity in Multi System Environments)
An active IETF working group standardizing fine-grained, least-privilege workload identity across multi-service/multi-cloud deployments, focused on REST/HTTP technologies. Deliverables include a **WIMSE architecture** doc (terminology, attestation, threat model), a **token issuance** doc (local issuance of WIMSE tokens by a limited-authority local issuer), and a **token exchange** protocol (exchange an incoming token for a workload-specific WIMSE token at security boundaries, with claim-mapping profiles) ([WG charter](https://datatracker.ietf.org/doc/charter-ietf-wimse/); [WG about](https://datatracker.ietf.org/wg/wimse/about/); [arch draft](https://datatracker.ietf.org/doc/draft-ietf-wimse-arch/)). **Relation to h2a primitives**: WIMSE's token model (signed, attested, scoped, exchangeable claims at boundaries) parallels h2a's mandate-scoped signed envelopes; the **token-exchange + claim-mapping** pattern is a plausible long-term standard route to translate an h2a attestation into a WIMSE token. **Caveat / staleness**: WIMSE is **in-progress IETF drafts**, not a finished standard — a forward-looking alignment target, not something to ship a connector against today.

## 3. Commercial NHI platforms (capabilities, not marketing)

Common shape across this category (2025-2026): agentless **discovery/inventory** of NHIs (service accounts, API keys, OAuth tokens, secrets, increasingly AI agents/MCP servers) across cloud/SaaS/on-prem/CI-CD/vaults; **ownership attribution** (map each NHI to a human owner/creator); **posture/risk** (overprivileged, stale, reused, vulnerable); **lifecycle** (rotation, offboarding); **threat detection/response**; and — a 2025 pattern — an **MCP server** for conversational query. They are *estate-wide governance planes*. h2a is the opposite scale: it knows *its own* agent instances deeply (signed identity, mandates, keyring) but not the org's whole estate. That asymmetry is the interop thesis: **h2a is an evidence/identity feed into one of these planes**, not a competitor to them.

- **Astrix Security** — discovery (incl. shadow/unregistered AI agents and MCP servers via a "four-method discovery architecture"), governance/agent-policy enforcement (right-sizing privileges), threat detection; attributes each identity to its human creator/vendor/env ([astrix.security](https://astrix.security/), [product](https://astrix.security/product/), [discovery](https://astrix.security/product/discover-non-human-identities/), [agent-policy PR](https://www.prnewswire.com/news-releases/astrix-security-delivers-the-most-comprehensive-ai-agent-discovery-and-enhances-security-with-agent-policy-enforcement-302719653.html)). **Notable**: Cisco announced **intent to acquire** Astrix on **2026-05-04** (terms undisclosed; an *intent*, not yet closed) ([Cisco blog](https://blogs.cisco.com/news/cisco-announces-intent-to-acquire-astrix-security), [SiliconANGLE](https://siliconangle.com/2026/05/04/cisco-buys-astrix-security-strengthen-ai-agent-discovery-governance/)). Sponsors the OWASP NHI Top 10. **h2a fit**: high — a governance plane that already speaks OWASP-NHI; could ingest h2a posture/attestation as an evidence feed for the agent-identity slice it cares about.
- **Oasis Security** — auto-discovery/inventory, AI/ML **ownership discovery engine**, posture management, **automated lifecycle** (provisioning incl. credential-based *and* federated identities, rotation, secure decommission) ([product](https://www.oasis.security/product), [ownership PR](https://www.prnewswire.com/news-releases/oasis-security-launches-industry-first-non-human-identity-ownership-discovery-engine-302292321.html), [provisioning blog](https://www.oasis.security/blog/introducing-oasis-nhi-provisioning-transforming-nhi-security-from-day-1)). **h2a fit**: medium-high — strong on lifecycle/decommission; an h2a `offboard`/attestation could be an upstream signal.
- **Entro Security** — NHI + **secrets** security; deep contextual scanning across code/cloud/CI-CD/SaaS; maps each secret to source/owner/risk; flags idle/orphaned secrets; automates rotation/vaulting/right-sizing/offboarding; **NHIDR** detection engine; owner attribution; Wiz integration ([entro.security](https://entro.security/), [product](https://entro.security/product/), [Wiz integration](https://entro.security/blog/entro-wiz-integration/)). **h2a fit**: medium — secrets-centric (h2a holds no secrets); intersection is posture/owner evidence, not key custody.
- **Token Security** — discover/govern/secure NHIs and AI agents; **unified identity graph** correlating agents, humans, secrets, permissions, data (blast radius); NHI posture management; shipped an **MCP server** (May 2025) for conversational query of inventory/posture/secrets/threats ([token.security](https://www.token.security/), [MCP server launch](https://www.businesswire.com/news/home/20250522606843/en/Token-Security-Launches-Industrys-First-MCP-Server-for-Non-Human-Identity-NHI-Security)). **h2a fit**: medium-high — graph model could absorb h2a instances/subagents as nodes with attested posture.
- **Clutch Security** — "Universal NHI" platform; contextualized inventory across Cloud/SaaS/on-prem/Code-CI-CD/Vaults/RPA/Data-Warehouses; proprietary **Identity Lineage** (origin, people, storage, consumers, accessed resources); posture, real-time detection/response; Zero-Trust/ephemeral stance; Universal NHI **MCP server** ([clutch.security platform](https://www.clutch.security/platform), [MCP server blog](https://www.clutch.security/blog/introducing-the-first-universal-nhi-mcp-server-intelligent-identity-lineage-tm-at-your-fingertips), [DarkReading launch](https://www.darkreading.com/identity-access-management-security/clutch-security-launches-with-nhi-platform)). **h2a fit**: medium — lineage model is rich; could attach h2a provenance/attestation as lineage evidence.
- **Natoma** — auto-inventory of NHIs (service accounts, API keys, OAuth tokens) across cloud/SaaS/on-prem; ownership/dependency context; least-privilege; monitoring/detection; on-demand & policy-based rotation; also a **hosted MCP platform** with auth/authz/governance for AI agents and 100+ prebuilt MCP servers ([natoma.ai launch](https://natoma.ai/blog/launch-announcement), [practical-NHI blog](https://natoma.ai/blog/a-practical-approach-to-non-human-identity); profile [nhimg.org/understanding-natoma](https://nhimg.org/understanding-natoma)). **h2a fit**: medium — both touch the AI-agent/MCP angle directly; Natoma as the governance plane, h2a as the agent's self-attested identity.
- **Aembit** — a **workload identity broker** (not primarily a discovery tool): no-stored-secrets, **just-in-time / per-task** credential issuance via Aembit Cloud (policy control plane) + Aembit Edge (proxy); verifies workload identity against trust providers (AWS IAM, K8s service accounts, GitHub Actions OIDC) and issues short-lived tokens; policy + agent-MFA for AI agents ([aembit.io](https://aembit.io/), [product](https://aembit.io/iam-for-workloads/), [secretless](https://aembit.io/glossary/secretless/)). Active in IETF WIMSE ([Aembit IETF blog](https://aembit.io/blog/inside-ietf-bangkok-shaping-the-future-of-workload-identity-and-access-management/)). **h2a fit**: medium — different layer (access broker, runtime), but the WIMSE-aligned token model is conceptually close to h2a's signed mandates; more an *adjacent identity layer* than an evidence sink.
- **GitGuardian (NHI Governance)** — secrets-detection heritage extended to NHI governance: **unified secrets inventory** as single source of truth across vaults; multi-vault integration (HashiCorp Vault, CyberArk Conjur, AWS/GCP/Azure secret managers, Akeyless, Delinea); per-NHI **knowledge graph** (where created/stored/used); hygiene analytics (vault coverage, secret age), overprivilege detection, remediation workflows ([gitguardian.com](https://www.gitguardian.com/), [NHI Governance launch](https://blog.gitguardian.com/gitguardian-launches-nhi-governance/), [NHI approach](https://blog.gitguardian.com/nhi-security/)). **h2a fit**: medium — secrets/vault-centric; h2a's no-secret posture is complementary evidence, not a vault feed.

(Other vendors exist in this space — e.g. SailPoint-adjacent and CNAPP entrants — surveyed at the adjacency level in §4 rather than enumerated exhaustively.)

## 4. Adjacent technologies

- **Secrets managers** — **HashiCorp Vault** issues **dynamic secrets** (generated on read, short-lived) and, in recent (Enterprise 2.0) releases, **workload identity federation** so Vault acts as an IdP issuing signed JWTs exchanged for short-lived cloud tokens — eliminating long-lived static credentials; documented AI-agent dynamic-secrets patterns ([Vault static/dynamic](https://developer.hashicorp.com/vault/tutorials/get-started/understand-static-dynamic-secrets), [secret-sync WIF](https://www.hashicorp.com/en/blog/advancing-secret-sync-with-workload-identity-federation), [AI-agent pattern](https://developer.hashicorp.com/validated-patterns/vault/ai-agent-identity-with-hashicorp-vault)). Cloud equivalents (AWS/GCP/Azure secret managers & KMS) play the same role. **h2a relation**: out of h2a's scope by design (h2a holds no secrets, consumes ed25519 keys provisioned elsewhere — see nhi.md NHI2). Interop is a **rotation handoff**: h2a's `nhi report`/`inventory` flags long-lived keys (NHI7) → a secrets manager performs the actual rotation. h2a is the *signal*, the manager is the *actuator*.
- **CIEM / CSPM (CNAPP)** — **Wiz**, Microsoft Defender for Cloud, Palo Alto Cortex Cloud (ex-Prisma Cloud, renamed 2025-02) compute **effective access** across human + non-human identities and surface over-permission/unused-entitlement risk; CSPM handles posture/compliance, CIEM handles entitlement risk (complementary) ([Wiz CIEM](https://www.wiz.io/solutions/ciem), [Wiz CIEM vs CSPM](https://www.wiz.io/academy/cloud-security/ciem-vs-cspm), [MS Defender CIEM](https://learn.microsoft.com/en-us/azure/defender-for-cloud/permissions-management)). **h2a relation**: these own cloud-entitlement truth h2a does not; an h2a attestation could be one *posture input* among many, but h2a does not see cloud IAM, so the overlap is narrow (NHI5 overprivilege at the agent/mandate layer only).
- **IdP service-account / workload-identity governance** — **Microsoft Entra Workload ID** treats applications, service principals and managed identities as workload identities, with Conditional Access, access reviews of service-principal role assignments (Workload ID Premium), and lifecycle workflows from planning to deprovision ([Entra Workload ID overview](https://learn.microsoft.com/en-us/entra/workload-id/workload-identities-overview), [Conditional Access for workload ID](https://learn.microsoft.com/en-us/entra/identity/conditional-access/workload-identity), [governing Entra service accounts](https://docs.azure.cn/en-us/entra/architecture/govern-service-accounts)). Okta has an analogous service-account posture. **h2a relation**: the IdP owns the authoritative directory of service principals; h2a agents are NHIs that could be *registered into* such a directory and have their attested posture reviewed there. Possible but heavier (directory write integration); lower priority than evidence-feed targets.

## 6. Candidate interop targets for h2a P3 (reasoned shortlist)

Three archetypes, ranked. Each answers a different P3 question ("standard vs vendor", "import vs export").

### #1 — SPIFFE/SPIRE: trust-anchor / credential interop (standards-first) — **recommended first**
**Why**: it is the closest *standard* to what h2a already is — h2a's signed-envelope-plus-keyring model maps **almost 1:1** onto SPIFFE's verifiable-credential-plus-trust-bundle model (correspondences detailed in §2), and SPIFFE Federation already defines a clean **public-key-bundle exchange** primitive. This is a *standard*, not a single vendor, so it does not bet P3 on one company (cf. the Astrix/Cisco churn). It is the lowest-risk, most durable target.
**Export shape h2a already produces**:
- The **attestation envelope** (`nhi attest`, `H2AEnvelope` with `body.kind = "nhi-attestation"`) is the verifiable credential analogue — ed25519-signed, channel-independent, verified against a known public key.
- The **keyring** (h2a's active public keys per instance, surfaced as `nhiKeyFingerprint`/`activeKeys`, rotated add→overlap→revoke) is the **trust-bundle analogue**. P3's concrete work: expose h2a active public keys in a bundle-shaped, fetchable form (a SPIFFE-bundle-style endpoint or a documented mapping `h2a instance id ↔ SPIFFE ID`) so a SPIFFE-aware verifier can validate an h2a attestation.
**Scope honesty** (as §2 establishes): h2a is *not* a SPIRE replacement. P3 here is **trust-anchor publication + ID mapping**, not "become an SVID issuer".
**Outcome**: this target was taken — designed in the [P3 interop spec](../docs/superpowers/specs/2026-05-28-nhi-p3-interop-design.md), core primitive shipped as `h2a nhi export` (DEC-094).

### #2 — An NHI-governance platform as an evidence-feed sink (vendor-first) — **recommended as the pragmatic concrete connector**
**Why**: this is the highest-value real-world integration — the governance plane wants *attested* posture for the agent-identity slice it discovers but cannot itself prove. Best-aligned candidates: **Astrix** (OWASP-NHI native, AI-agent focused — but de-risk for the unclosed Cisco acquisition), **Token Security** or **Clutch** (graph/lineage models that can absorb h2a instances as nodes; both expose **MCP servers**, which is a natural fit since h2a *is* an MCP server). 
**Export shape h2a already produces**:
- The **posture report** (`nhi report`, `H2ANhiPostureReport`) is already OWASP-NHI/CSF-shaped → ingests as a posture finding set keyed by `risk` (NHI1/4/5/7/9) + `csf`.
- The **inventory** (`nhi inventory`, `H2ANhiInventory`) maps onto the platform's inventory: each h2a `instance`→an NHI node, `keys[].fingerprint/longLived/sharedWith`→credential metadata + reuse edges, `subagents[]`→delegated NHIs, `offboarded`→lifecycle state.
- The **attestation envelope** is what makes the feed *trustworthy* (signed provenance: who attested what, verifiable independently).
**Concrete first cut**: POST the signed attestation envelope (which embeds the posture report) to the platform's ingestion API; map `findings[]`→risks, `summary`→counts. Direction is **h2a → platform** (export). Caveat: I verified these platforms expose query/MCP surfaces and rich inventory models, but did **not** verify a documented *inbound posture-ingestion API* for each — that verification is itself a P3 task.

### #3 — Secrets manager as a rotation actuator (handoff) — **secondary**
**Why**: complements rather than competes. h2a detects NHI7 (long-lived keys) in `report`/`inventory` but, by design, holds no secrets and does not rotate the underlying material. **HashiCorp Vault** (or cloud KMS/secret managers) is the actuator.
**Export shape**: the **inventory** `keys[]` entries with `longLived: true` (and `ageDays`) are the work-list; the handoff is "h2a says rotate key X on instance Y; Vault performs the dynamic-secret/credential rotation". Direction is **h2a → manager** (export of a rotation signal); h2a does not import secrets back. This is the narrowest, most clearly-bounded integration.

## 7. Open questions for the P3 decision

1. **Standard vs vendor first?** SPIFFE/SPIRE (durable, standard, no single-vendor bet) vs a concrete NHI-governance connector (higher immediate utility, but vendor-specific and — for Astrix — mid-acquisition). Recommendation leans SPIFFE-first for durability, with one vendor evidence-feed as the proof-of-utility.
2. **Which vendor, given the Astrix→Cisco intent-to-acquire (2026-05-04, unclosed)?** Build against the most stable/OWASP-aligned target, or one with an open MCP server (Token/Clutch/Natoma) to reuse h2a's existing MCP nature?
3. **Build location** — in `@sentropic/h2a` core, or in `../sentropic/` connectors? nhi.md (P3 row) and BACKLOG.md both flag the connector likely belongs in `../sentropic/` to keep core protocol-pure; needs a DEC to confirm.
4. **Export vs import** — P3 as defined is mostly *export* (push posture/attestation out). Is there a P3 case for *importing* external inventory into h2a's registry view, or does h2a stay export-only (keeping the registry authoritative for its own instances)?
5. **Ingestion-API verification** — do the shortlisted governance platforms actually expose a documented *inbound* posture/evidence-ingestion API (vs query/MCP-read only)? This survey did not confirm inbound APIs for each vendor; that is a prerequisite verification before committing to target #2.
6. **Transport** — does P3 push the raw signed envelope (preserving verifiability end-to-end) or a translated per-target payload (losing the signature unless the target understands ed25519)? SPIFFE/WIMSE token-exchange suggests a translation path; evidence feeds suggest passing the signed envelope intact.
7. **WIMSE timing** — WIMSE is draft-stage; do we track it as a future alignment (and design the export so a WIMSE token-exchange could consume it later) without building against it now?
