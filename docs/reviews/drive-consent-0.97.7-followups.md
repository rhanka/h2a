# Drive peer consent 0.97.7 — known limits and debt follow-ups

Non-blocking items surfaced during the independent reviews and the isolated measurements. None blocks the 0.97.7 publication (CI is green; the authority core is CLEAN and no path authorizes wrongly). Each is written here so it is not rediscovered blind later. The canonical Track entries are h-cond's to record; this file is the ready-made evidence.

## Documented residual behaviours

### R1 — Direction-A residual: principal assigned AFTER pruning (never toward grant)
If instance B has no principal when its grant G1 is pruned as non-decisive, and a principal is assigned to B *afterwards*, the warm derived index returns `consent-expired` while the full-journal `projectConsent` returns `consent-principal-unavailable` for that request. This is a divergence within the refusal side only — **it is NEVER toward GRANT**; the drive stays blocked on both paths. It is NOT reachable through the API: `registerInstance` keeps the first registration and `findInstance` takes the first row, so it requires a hand-rewrite of `instances.jsonl` between the grant and the pruning (as the review's isolated harness did). It self-corrects at the next index rebuild (≤60 s on the server via the periodic tick, immediate on CLI reopen). Documented per the reviewer's request. Source: opus 5.5 review, section (1)(c).

## Debt follow-ups (track separately)

### D1 — rebuild vs write pair-consistency asymmetry (open with the counterexample)
`recordDriveConsentEnvelope` enforces pair consistency on WRITE (`event.negotiationId !== consentPairId(from,to)` → reject), but `rebuildConsentIndex` does NOT enforce it on REBUILD — it feeds every non-audit entry of the negotiation journal into `pruneConsentIndex` regardless of each payload's `to`. The rebuild path is therefore MORE PERMISSIVE than the write path. In the documented threat model (same-uid key guard, forgeable journal), a lane can hand-write a journal and seed the index with foreign-target evidence (a grant whose `p.to` differs from the pair). NOT a blocker: `projectConsent` re-verifies signatures and checks pair identity, so nothing is authorized wrongly — this is exactly what let the memoization stay exact. But an asymmetry where rebuild accepts what write rejects is the kind of hole that opens later when someone trusts the index one step further. Attachment: `findinstance-counterexample.json` (the mixed-target index that this asymmetry makes constructible). Discovered via the findInstance-hoist counterexample.

### D2 — findInstance has no cache/index (global, 38 sites) — slowness item
`findInstance(id) = listInstances().find(...)` re-reads and re-parses the whole `instances.jsonl` (~16.7 MB, ~55 ms) on every call; 38 call sites. The 0.97.7 lot fixes ONLY the per-grant repetition inside `pruneConsentIndex` (commit: per-prune memo). The global registry cache (mtime-invalidated, or an id index) is a cross-cutting change touching 38 sites and is tracked on the slowness item `01M38NYH7X3TVBV5TA4KJS3Q8W`, its own cycle + review. Related: registry is ~85% dead (see the slowness doc), a second independent lever.

### D3 — `findInstance` date-dependency for the "no-principal" rule (see R1) — hors-API, self-corrects at rebuild.
### D4 — static import cycle store.ts → mcp/identity-state.ts → identity/live.ts → store.ts. Pre-existing (before 004a1dff), load-safe (the constant is read only at call time). Fix: move MCP_IDENTITY_TIMEOUT_MS to a leaf module. Non-blocking.
### D5 — `readdirSync(paths.negotiations)` in verifyConsentHistory has try/finally but no catch. Pre-existing (before 004a1dff). If the negotiations dir exists but is unreadable (EACCES) or is a file (ENOTDIR), createLocalStore throws; in the 60 s server timer that would be an uncaught exception. EROFS does NOT trigger it, and all 2b marker I/O IS protected. Non-blocking; harden with a catch.
### D6 — 2b marker replay is unbounded on a root that WENT read-only AFTER a crossing (the unlink to clear it fails, so every CLI command re-emits). Real debt telemetry, not a fault. Non-blocking.
### D8 — the memo's "coherent view" is registrations-only, not the keyring. The per-prune `findInstance` memo (commit cdd9813b) gives a coherent view of `instances.jsonl` (registrations) for one prune. It does NOT extend to the keyring: `listKeyEvents()` (used by `verified(..., historical=true)`) and `listInstanceKeys()` still re-read per call, so a registration/keyring version-mix remains possible exactly as before the memo. Not a regression; recorded so the commit's "coherent registry view" wording is not over-read as covering keys. Source: opus 5.5 memo re-review.
