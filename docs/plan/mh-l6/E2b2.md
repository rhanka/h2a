# E2b2 — boot réel, journal, identité et portée des lancements Node

Le boot MCP de production lance désormais `runtime/upgrade/boot-worker.js`.
Cette entrée vérifie son image avant de charger son moteur relatif et accepte
seulement root/TTL/mode. Elle conserve le travail de maintenance hors du
processus stdio. La garde d'image reste hors du catch best-effort du moteur.
Les résultats du moteur sont attendus, y compris lorsqu'ils seront asynchrones.
L'ancien export `MCP_UPGRADE_WORKER_SOURCE` reste une API de compatibilité pour
les consommateurs extérieurs ; il n'est plus le lanceur de production.

Les lancements distinguent le fichier exécuté des arguments métier. Le fichier
et les alias de Node sont reconnus par leur chemin physique ; les arguments
suivant une entrée identifiée restent opaques. Cela évite de traiter une donnée
comme une entrée ou de résoudre un chemin illisible fourni par un outil.
Les URI file sont reconnues et les formes Node de chargement non qualifiées,
notamment `--entry-url`, sont refusées avant création du processus d'image.
Les formes shell/eval ambiguës qui référencent l'image restent refusées.
Il n'y a aucune liste de serveurs MCP ou de builds.

Le rouge du vrai boot lance le vrai runMcpServe sans runtime d'upgrade injecté :
le worker eval exécutait un module modifié après la vérification par son parent.
Le témoin de cet effet est observé sur Node 22 et 24. Le worker fichier protégé
refuse le payload altéré et le serveur stdio termine normalement sur son propre
signal d'arrêt de fixture. Les alias de fichier, alias d'exécutable Node et URI
d'entrée ont également produit un effet extérieur avant correction.

Les fixtures utilisent les vrais modules construits : journal natif (fork puis
Worker d'I/O), forkIdentityWorker et moteur de check/auto du worker fichier.
Le journal reçoit un événement typé de fixture et écrit réellement sa ligne ;
**aucun host natif n'est lancé**. L'identité explicite est résolue sans PEM et
reste inéligible à une délégation. Les altérations tardives du journal et du
worker d'identité sont refusées. Les PID/naissances des enfants observés sont
capturés à spawn et leurs sorties sont attendues ; aucun état de l'owner.

Les quatre API spawn/spawnSync/execFile/execFileSync acceptent une application
Node extérieure recevant le manifeste comme donnée. Les entrées internes
conservent le lecteur et refusent leurs imports extérieurs. Fork et Worker sont
couverts aussi par les fixtures précédentes et les chemins réels ci-dessus.
Les caches sont frais, npm est offline et le préfixe de la fixture est imposé
pour le cas auto. Le cas auto qualifie le moteur actuel déjà-cible ; l'adoption
H4 avant ce raccourci est toujours F/C2.

## Qualification

Les sorties finales sont conservées sous `evidence/*-final-E2b2.log` ;
`proof-E2b2.json` vérifie chaque reçu et les restaurations.

| `upgrade-boot-worker.test.js`, `mcp-stdio.test.js` | 3 + 16 | 3 + 16 |

| `node scripts/mh-l6-components-mutate.mjs` | 16 rouges ERR_ASSERTION / 16 restaurations vertes | 16 / 16 |

Les 16 paires correspondent à dix points de faute, avec plusieurs API/oracles.
Neuf oracles provoquent un effet de code extérieur ou un import devenu permis.
Les sept autres portent sur disponibilité, portée des données et profil de
chargement. Revenir au boot eval est maintenant bloqué aussi par la garde URI :
ce mutant casse le lancement attendu et est tué par code -1 au lieu de 1, sans
exécution altérée. Le rouge initial antérieur à ces deux corrections observait
bien le témoin créé. Cette distinction est conservée, sans attribuer au mutant
une fuite qu'une autre garde empêche.

Le mutateur initial a refusé la cible compilée `function (` avant le dixième
point, après neuf paires : sa recherche attendait `function(`. Tous les fichiers
ont été restaurés et leurs SHA vérifiés ; le diagnostic est conservé dans
`components-mutator-whitespace-diagnostic.json`, hors preuve produit. Après
correction de la recherche, les seize paires ont été rejouées sur les deux Node.
Le header du runner affiche désormais correctement MH_L6_CASE ; les anciens
rouges restent bruts avec leurs vrais noms TAP et leur compte unitaire.

`node node_modules/typescript/bin/tsc -b packages/h2a --pretty false` : exit 0,
sans diagnostic, après restauration. `node scripts/mh-l6-e2b2-audit.mjs
/tmp/mh-l3-qualification-YeHHOv/source` : exit 0, 31 fichiers identiques, huit
émissions, 75 tests et seize paires/profil, six sources natives inchangées depuis
`84492d9a`. Ceci ne qualifie pas les octets du payload publié .6.

## Limites conservées

| NOT covered / suite obligatoire | Lot |
|---|---|
| Démarrages réels des autres entrées natives (op/process/supervisor/launch-guard), sonde native legacy encore en eval, graphes et paquets publiés | E2b3/E3/F |
| Drain/fatal/PTY/relance et latence des vrais hosts, gel comparatif du payload .6, chaîne native de release épinglée | E3/MH-L8 ; les sources natives demeurent inchangées |
| Producteur maintenu de fermeture v1 et vrais .5/.6, bootstrap/adoption physique, désadoption/npm | B2/C2/D/F, frontière M18 |
| Moteur H4 commun CLI/auto, adoption déjà-cible, autorités et tickets de bout en bout, consolidation finale des anciennes mutations | F |
| Revue indépendante, performances/endurance et profils non qualifiés | Conducteur/MH-L8 |

La qualification porte sur les chemins et options exercés. Les autres formes
Node/Worker et alias d'exécutables non résolus restent à qualifier. Les modules
non adoptés de développement et les applications extérieures conservent leurs
parcours. Les artefacts MH-L1 restent des snapshots ; core/runtime 0.98.5 et
leur enveloppe prototype ne sont pas une release 0.98.7.

Aucun fichier natif n'est modifié, aucun switch MCP live n'est initié, aucune
découverte registry n'est ajoutée. Aucun retrait de la spec.
