# B1 — délégation et récupération de l'autorité H4

Le journal passe durablement à `DELEGATING`/`REVOKED` avant que le candidat
exact puisse acquérir. Le ticket privé lie révision, epoch, identité de naissance,
build et manifeste sélectionnés. Le candidat vérifie son entrée absolue puis
publie un reçu et sa nouvelle autorité avant acquittement. Les reprises d'ACK
conservent révision/epoch ; une erreur fsync impose une nouvelle synchronisation.

Une délégation abandonnée par un candidat prouvé mort peut être réémise avec
un nouvel epoch. Un contrôleur acquis et mort peut également être remplacé par
le contrôleur de l'image sélectionnée, jamais par réactivation de la source.
Une identité vivante ou un cadre de processus incomparable interdisent cette
récupération. Aucune stratégie MCP vivante n'est appelée.

Chaque opération reprend le vrai verrou de succession compatible avant le
flock H4. Un gardien vivant bloque l'acquisition ; sa mort prouvée permet la
succession réelle du verrou, sans ancien jeton supposé encore valide.

Le rouge initial constate l'absence des sept comportements de délégation. Le
premier essai d'intégration est invalide : neuf annulations dues à l'attente
de `ChildProcess.close`. Les diagnostics privés montrent `exit 0`, fermeture
des deux pipes, mais aucun `close` agrégé après déconnexion IPC dans cette
fixture Node 22. Le test attend ces trois événements séparément. Aucun de ces
essais annulés n'est compté comme preuve.

Après cette correction de fixture, deux rouges par assertion établissent la
resynchronisation manquante d'un reçu visible et d'une autorité acquise dont le
fsync avait échoué. Un autre rouge établit l'absence de récupération après mort
du délégué. Ils sont conservés avec leurs codes non nuls. Les tests de mort
signalent uniquement des PID qu'ils ont créés ; les secrets ne sont transmis
ni par argv, ni par environnement, ni dans la sortie de test.

Le rouge de révision de récupération montre également qu'une mort prouvée
ne permet pas de réparer implicitement un ticket/journal discordant. Ce refus
est vérifié séparément de celui d'acquisition. Le motif du premier essai de
mutation de cette garde était devenu ambigu après l'ajout du second refus ;
aucun mutant ambigu n'est compté, les deux gardes sont ensuite tuées séparément.

Les mini-images sont des exécutables de test qui importent le contrôleur compilé
depuis la copie source privée : preuve de persistance/exclusion, pas de packaging
fermé. Les gardiens sont des processus de test ; aucun service persistant produit
n'est créé ici. `proof-B1.json` lie les octets, les profils et les reçus.
