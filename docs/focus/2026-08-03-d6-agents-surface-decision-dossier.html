En une lecture — de quoi il s'agit vraiment

Cette spec pose un contrat : que les agents de tous les hôtes (cowork, plugins, sessions chat, jobs, transcripts CLI) deviennent des lignes d'UNE seule surface (AgentsFeedPort → AgentsList), au lieu de 2–5 listes séparées. C'est le premier morceau concret de « capitaliser sur sentropic » (D6) : sentropic livre la LIB (le composant + le port), chaque hôte câble son INTÉGRATION (la source qui enrôle ses agents).

HONNÊTE Ce que signer ne fait PAS : ça ne fait PAS apparaître tes agents sur la surface. Cette slice livre le contrat + le port + des tests-fixtures. Les vraies sources de données (donc tes agents cowork/plugins/remote qui apparaissent) sont gatées sur un autre blocage (BR-39l, le trou de feed) + le storm-gate 0.90.1 + ta signature. La signature est en amont de ton besoin réel (cowork+chat qui marche) : elle acte la forme du contrat, pas la livraison.

Les décisions de spécification (commentées, avec le risque)

D-1
La frontière LIB / INTÉGRATION (le cœur du « capitaliser sur sentropic »)
Décide sentropic livre la LIB (@sentropic/chat-ui : le composant AgentsList + le contrat AgentsFeedPort/AgentsEntry). La LIB rend et définit le port ; elle ne fetch pas, n'enrôle pas, ne détient aucun hôte. Chaque hôte câble l'INTÉGRATION = la source de feed qui enrôle ses agents (présence h2a, hôte plugins, connecteur cowork).
Sujet C'est LA décision de délégation : qu'est-ce que tu délègues à sentropic (la surface + le port) vs ce que h2a/les hôtes gardent (le feed).
Risque Une frontière mal posée = couplage/dette (exactement ce que D6 veut éviter). Si sentropic possédait aussi le feed → les hôtes se couplent à son modèle de données. Si chaque hôte possédait la surface → retour aux « 2 ni 5 » listes.
archi h2a : ACCEPTE — B1 « la LIB n'enrôle pas » VÉRIFIÉ EN SOURCE (le port n'expose que list()+subscribe(), structurellement incapable d'enrôler)terra : B1 présent, split confirmé
D-2
Un seul port ; les entrées sont des GENRES, pas des surfaces
Décide UNE AgentsFeedPort, UN AgentsList. Cowork/plugins/sessions/jobs/CLI = des entrées (kind: agent|session|remote|job|run) avec connection + hostKind — pas un 2ᵉ composant. AgentsList rend l'union.
Sujet Unifier la surface agents (« une, pas deux ni cinq »).
Risque Forcer des hôtes hétérogènes dans un même modèle d'entrée : si l'agent d'un hôte ne rentre pas dans le modèle de genres, il est exclu ou bricolé.
archi h2a : ACCEPTE — « le modèle de fusion est juste : un port, entrées=genres, provenance explicite »
D-3
3 champs AJOUTÉS à AgentsEntry (et l'honnêteté d'état)
Décide ajouter à AgentsEntry : agentRef (identité durable, pour I1), marqueur HOLDER/VIEW (autorité, pour I3), measuredAt (mesuré-vs-supposé, pour I2).

D-4
Identité durable (I1) : réservée, PAS soudée — et la réparation DIFFÉRÉE ⚠️
Décide clé un agent sur agentRef, JAMAIS sur providerSessionId/un id de conversation. La spec ENREGISTRE le défaut connu (reclaimOrMint matche host+providerSessionId → la reprise ne se déclenche jamais → une identité fraîche est mintée silencieusement) et réserve le slot + vise l'identité reprise, mais ne répare PAS le chemin de resume (hors-scope, feed-time).
Enjeu réel C'est un bug d'identité ouvert (déjà connu côté h2a, WP5). Signer cette slice ne le RÉPARE PAS — elle réserve le slot et diffère le fix. Donc l'identité durable est contractée mais pas encore fonctionnelle ; la conformité I1 ici est partielle (réservée, non réparée). Tu dois le savoir : ce n'est pas « I1 réglé », c'est « I1 réservé, réparation à venir ».
archi h2a : le « réserver-pas-souder » est la bonne discipline (lié à son propre invariant surface/I1, publié en #152)
D-5
I3 détenteur/vue · I4 un seul vocabulaire (testables)
I3 chaque entrée = HOLDER ou VIEW ; le renderer ne persiste RIEN d'une VIEW ; en désaccord le DÉTENTEUR gagne (jamais la vue).
I4 les capacités des agents plugin/cowork passent par le vocabulaire cross-host EXISTANT ; aucune 2ᵉ grammaire. Testable maintenant.
Risque faible — ce sont des invariants de discipline ; le risque est de les contourner au feed-time (d'où les fixtures qui les gardent).
archi h2a : ACCEPTEterra : conformité présente
D-6
I2 / I5 : RÉSERVÉS, PAS encore appliqués (feed-time, gaté) ⚠️
Décide I2 (mesuré vs supposé) et I5 (une opé sur une contrepartie injoignable ne doit jamais ressembler à un succès : DÉPOSÉ-EN-ATTENTE pour réveil, ou refusée PAS-FAIT) sont réservés mais lient au feed-time (gaté). Donc PAS appliqués dans cette slice, seulement réservés pour que le feed ne puisse pas les contourner.
Enjeu I5 est l'invariant sur lequel s'est jouée toute la revue (le « dépôt-dormant-pour-réveil » dont 11 lanes dépendent). Il est maintenant correctement rédigé (principe), mais seulement réservé — son application réelle est au feed-time.
