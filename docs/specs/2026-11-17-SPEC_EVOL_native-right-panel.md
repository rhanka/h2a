Collapsed mode (panel closed, feature enabled): the CLI keeps its width minus **one** reserved marker column, and the bottom bar carries the clickable toggle marker:

```text
┌────────────────────────────────────────────────────────────────────────────┬─┐
│ CLI (full width minus 1 column)                                            │*│  lit: another session needs attention
├────────────────────────────────────────────────────────────────────────────┴─┤
│ … bottom bar …  ▸▸  (click opens the panel; F12 too)                       │ │
└────────────────────────────────────────────────────────────────────────────┴─┘
```

Loop state is never implicit. Every session row resolves to exactly one of these displayed states (§5.2); `*` appears exactly on the rows that need the owner:

```text
no objective bound ──► "no objective"            (no loop expected, no *)
engaged, no loop ────► "↻ NO LOOP *"             (Track-engaged work, no h2a loop yet, §5.2)
objective candidate ─► "objective available"     (unbound Track work exists; no * in v1, §5.2)
bound + engaged ─────► "↻ native" or "↻ h2a"     (mechanism named, last tick/verdict shown)
bound + native ? ────► "↻ native ?"              (native tool, no attestation yet — no *, §5.2)
bound + NOT engaged ─► "↻ NOT ENGAGED *"         (the 19:05/19:10 alert case)
bound + unattended ──► "↻ unattended"            (word + header count, no per-row *, §5.2)
bound + waiting ─────► "↻ waiting-human *"       (decision/question blocks the loop)
terminal ────────────► "↻ done / stopped / …"    (word shown, * only on blocked/failed)
source unreadable ───► "loop unknown ?"          (never rendered as engaged or as clear)
```

## 1. Purpose, scope, non-goals

The bottom status bar (PR #443, merged) proved the pattern: the native terminal host reserves screen space the child CLI never sees and renders h2a state there. The owner asks for the same pattern on the right: a retractable panel that makes the fleet of sessions, the pending decisions/questions, the Track state **and the objective-loop state of every session** visible and actionable without leaving the current CLI — by keyboard **and by mouse click**.

In scope: one reserved right area in the native attach view (open panel + 1-column collapsed marker); read models reused from `h2a restore`, the status projection, the loops store and Track; per-session objective binding and explicit loop state, including objectives spanning several projects at meta-workspace level; engagement of loops through each CLI's native mechanism where one exists, with the h2a objective loop as the named fallback; a Track pane summarised only through the existing gateway; asynchronous decision answers over `h2a send`; a keyboard + mouse scheme that survives the owner's real terminal (VTE 0.84).

Out of scope: any implementation in this PR (lots in §12 are the implementation contract); a new provider, credential or network route; a second grouping, objective or loop store; silent auto-enrolment of loops (see §5.4 — the default rule is *expected + alerted + one action to engage*, never invisible enrolment); changes to Track's writer rules; tmux-hosted rendering beyond what existing projections report; mobile or web rendering.

## 4. Layout contract

### 4.1 Reserved geometry and enablement (mirrors the bottom bar, column axis)

The panel is a second reserved area owned by the attach layer, exactly as the bottom bar is (F1). The child PTY never learns the full terminal size:

- **Feature flag (L0 surface, B2).** Env `H2A_RIGHT_PANEL` wins over config `rightPanel.enabled`; default **OFF**. With the flag off, nothing is constructed and attach behaviour is byte-identical to today (L0 acceptance proves it). Width: `H2A_RIGHT_PANEL_WIDTH` > `rightPanel.width` > **32**, clamped to 20–60. Unreadable config means “not enabled” for the panel (inverse of the bar's F5 default, because the panel changes child geometry and mouse mode); attach never crashes on config either way.
- **Open:** child receives `cols − panelWidth` columns and `rows − 1` rows (bottom bar unchanged). **Collapsed (feature on, panel closed):** child receives `cols − 1` columns; the single marker column (B3) stays reserved for the whole attach so open/close are the only two child geometries. **Feature off:** child receives full `cols`.
- **Minimums.** Opening is refused (marker kept, panel stays collapsed, no layout corruption) when the child would fall below **40 columns** (B3); the existing ≥ 10-row rule for the bottom bar is unchanged, and below it neither reserved area paints. Width is fixed per attach in v1 (no drag-resize); changing it is a `/c` setting applied at next open (§8/§9, lot L7). **Bar inactive** (bar disabled by env/config, or < 10 rows while the panel feature is on): the panel spans rows `1..rows`, `y = rows` belongs to the child/panel zones (§9.3), and the only toggles are the marker column and the opener key — no bottom-bar marker exists to click. (#465 as shipped always routes the last row to `status-marker` and paints `rows−1` lines; L0.5 owns this branch.)
- **Column containment (normative; the outer terminal is assumed to ignore `?69`).** There is no DECSTBM equivalent on the column axis in VTE (`?69`/DECSLRM support is `unverified` — Annex D holds no VTE probe; L0.5.6 probes it), so “clip like rows” is not a mechanism. The attach layer keeps a **child-sized** headless model (`childCols × childRows` — including the model the bottom bar reads) and guarantees after **every** child output batch, in open **and** collapsed states: (i) reserved cells (`x > childCols`, `y < rows`) equal the panel/marker render; (ii) child-area cells equal the child headless model. To hold (i)/(ii) it emulates the child's autowrap at `childCols` (pending wrap ⇒ explicit CR LF inside the scroll region — without this the next glyph lands in the reserved column); clamps CUP/CHA/HPA/CUF/HT targets to `childCols`; rewrites EL 0/2 to ECH bounded at `childCols`; and marks the reserved area dirty after ED, ICH, DCH, ECH, REP, IL, DL, SU, SD, region scrolls, RIS/DECSTR and alternate-screen switches, repainting it before the batch is flushed. Whether the open panel renders by (a) passthrough + this containment, (b) composition in the outer alternate screen, or (c) overlay without child resize is **OQ-18** (recommendation: (a) through L0.5, (b) evaluated in L1).
- **Cursor/margin hygiene.** The panel **never uses DECSC/SCOSC** (`ESC 7`/`8`, `CSI s`/`u`): after painting it restores cursor, SGR and origin/insert modes from the child headless model, as the bottom bar does. The save slot is shared with the child, and under DECLRMM `CSI s` stops meaning “save cursor” at all (Annex B) — both make `#465`-style `CSI s` painting corrupt child cursor state. **No lot before L1 emits `?69`/DECSLRM** (no benefit on VTE, changes `CSI s` where honoured); a later lot may enable it only with child `CSI s`→`ESC 7` and `CSI u`→`ESC 8` rewriting while it is on. (#465 as shipped does both; L0.5 removes them.)
- **Stated L0.5 limits.** With containment (a), fragments of the *open* panel enter the outer scrollback when the child scrolls, and the reserved area is repainted after every dirtying batch (output-rate paint, not just 1 Hz). Both are accepted, named limits of the passthrough design — not bugs to discover later; OQ-18(b) is the exit if scrollback pollution proves unacceptable in use.
- **Repaint and restore.** Snapshot-driven repaint, at most one time-driven repaint per second (F1 rates). Resize/detach/exit/reconnect restore full geometry, child modes (F3 reset/restore symmetry), mouse reporting (§9.3) and margins. A panel fault degrades to `?` in the marker column — never a corrupted child screen, never a fabricated all-clear (F6 posture).

### 4.2 Meta-workspace tabs and the session tree

- **Tabs = restore windows (R8), de-capped and stabilised.** One tab per non-remote `LayoutConfig.groups` entry, **uncapped**; all ungrouped projects in **one stable `other` tab** ordered by project name; no `maxPerWindow`/`sharedWindows`/`multiSession` cap applies to the panel, and a live session is never hidden by overflow (corrects raw `groupSessions` behaviour, F8 — restoring a window may cap, *watching* the fleet may not). Tab label = group title (`other` for the ungrouped tab). No panel-specific grouping config in v1; a derived **Attention** tab (blocked/question/loop-gap across workspaces) adds no config and is proposed as OQ-8 — it is *not* in L0. (#465 as shipped renders whatever groups the injected snapshot carries; this derivation is L0.5/L1 production wiring.)
- **Sessions = active sessions as restore sees them (R9), made precise.** The list is the restore inventory (registry sessions merged with scan discovery, F7) restricted to (a) the tab's projects and (b) sessions with positive liveness evidence in the same views restore/host code already consults (registry row not ended + native-host or tmux presence). Dead-but-restorable rows (which restore would *relaunch*) are **not** “active”: they are omitted from the main list and, from lot L1, reachable under a `▸ n restorable` expander so nothing restore knows is hidden. Scan-origin (`unclassified`, transcript-guessed) rows join the main list only when matched to **exactly one** live host session (same tool + cwd in the native/tmux view); zero or several candidates ⇒ the row stays out of the main list (`unknown`, never guessed — one cwd routinely hosts several live sessions). Matched rows keep an `unclassified` marking (§10) rather than being promoted to human sessions, and unmatched scan rows fall back to the restorable expander. A session appears in exactly one tab; dual-host-ambiguous identities (F7 resolver `ambiguous`) appear once, marked `unknown`, with no action enabled on them.
- **Status derivation (normative source → value, first match wins).** The L0 enum `running|idle|waiting|paused|blocked|failed|question|decision|unknown` (§11) is derived, never stored twice: an **OWNER GATE record targeting the session** (§4.3) ⇒ `question`; a pending decision **attributed to the session** (§7.3 tiers) ⇒ `decision`; drumbeat `workStatus` (F17) `blocked` or `out-of-tokens`, loop-agent status `rate-limited`/`out-of-tokens`, or gateway `retryAfterMs` active ⇒ `blocked` (the *word* in the selection line keeps the cause: `blocked · out-of-tokens` etc.); loop-agent `dead`/`failed` ⇒ `failed`; `workStatus: paused` ⇒ `paused`; `workStatus: working` ⇒ `running`; loop `waiting-agent` or CI-wait evidence ⇒ `waiting`; a live session with no work evidence ⇒ `idle`; **no readable evidence ⇒ `unknown`** — never `idle` by default. Loop-agent `awaiting-decision` maps to `decision` when the gating decision resolves (§7.3), else `question`.
- **Row content.** Status symbol + colour + `*` (§10), session label, tool, gateway short form in the bottom-bar vocabulary (`gw` + `requested→upstream` when observed, `direct`, `gw ?` when unknown, F6/F22), and — from lot L2a — the explicit loop token of §5.2 (e.g. `↻ native`, `↻ NOT ENGAGED *`). In L0/L0.5 the loop token is absent (not faked as engaged or clear); §12 states this limit in the L0 PR body.
- **Sub-sessions (R11).** Delegated executions (F9) are hidden by default under their delegating human session as `▸ n delegated`, expandable in place (keyboard and click). They never appear as top-level human rows. Executions whose delegator cannot be proven degrade the expander (`deleg ?`) instead of being attached by guess (F9).
- **Loops/objectives browsing (R11).** From lot L2a each enrolled session carries a `▸ objective/loop` expander (loop status, last tick/verdict, attendance, attestation age); lot L2b adds bound-objective refs and the meta-workspace objectives list of §5.5. In L0/L0.5/L1 loops are not rendered in the panel; the bottom-bar `L` counter stays as-is (with F16's drift called out until L2a reconciles it).
- **Selection.** One selected session (reverse-video row, §10). Selecting drives §4.4 (bottom-bar delegated names) and §4.3 (sub-pane target); it never steals CLI input focus (§9 focus model) and never attaches as controller to another session (F4).

### 4.3 Decisions / questions list and the bottom sub-pane

- **Sources (R4).** From the journal of record (next bullet): Track decisions with `outcome ∈ {pending, deferred}` (F20); questions = dossier `qa[]` entries without an answer; **OWNER GATE records** (2026-11-07 spec D3 — the recorded “this session has a question” signal, carrying target instance + session); plus, from lot L2b, objective loops in `waiting-human` (F12) and h2a inbox envelopes addressed to the owner of type question/escalate. **Recorded deviation from the build brief:** the brief named “Track pending decisions, h2a messages” together; L0/L0.5 ship Track + OWNER GATE only and **h2a-message questions are deferred to L1** (§12 states this in the L0 PR body — the deviation is named, not silent). One list: decisions first, then questions, oldest first within each class; each row shows `◆`/`?`, `*` while **pending** (never on `deferred`, §10), short title, age, concerned workspace/session when *derived* (next bullet), and the dossier link text when *derived*.
- **Journal of record (normative; replaces “nearest-ancestor `.track`”).** `.track/events.jsonl` + `head.json` are git-tracked, so every linked worktree carries a copy frozen at its branch point: reading “the nearest `.track`” from a worktree session reads stale decisions, and writing there writes into a PR branch (owner rule: **no `.track` writes in PR branches; h-cond is the single writer of the live h2a store**). Each project's Track source is therefore resolved **explicitly, never from the session cwd**: (1) a per-project `trackDir` in the panel config (`rightPanel.trackDirs`), else (2) the repository's **main checkout**, never a linked-worktree copy. Rows cite the resolved directory; a session running in a linked worktree reads its repository's journal of record. Decisions are read from the journal of record of each project in the current tab; a project without a readable store contributes a `decisions unknown (?)` line — never an empty-list all-clear. L0 as shipped (#465) reads no store by default (B4); single-store reading against the journal of record is L0.5, multi-store is required by L1 at the latest (§12). Who may *write* is §7.2's writer policy (OQ-17). This bullet is reprised verbatim wherever §5.5/§6 say “its project's store”.
- **Dossier link + concerned session: derivation, not stored fields.** Track has no `dossier.path/url/link`, `dossierLink` or `sessionId` field (F20) — #465 reads exactly those guessed fields, so no production link ever appears (B4). The link is *derived*: sources are `dossier.artifacts[]` in addition order, then item `links[]` with kind ∈ {artifact, spec, decision}; classes: relative `*.md` ⇒ resolved against the journal-of-record root, rendered as text; `https://claude.ai/…` ⇒ Claude artifact, system opener; a URL issued by the Sentropic publish client (`packages/h2a-runtime/src/sentropic/`) ⇒ Sentropic artifact, system opener; `h2a-decision-dossier` ⇒ show `negotiationRef` + render via `track focus <id> --workspace <w>`; `chat:` or unknown ⇒ text only, labelled “not openable”. `sessionId` = §7.3 resolution tiers (b)/(c) only, else absent. ### 4.5 Collapsed marker column (1 column)

- **Lit rule (R17, made countable — r3 rewrite).** Owner trigger: “as soon as **another session** is blocked or has a question” — a *session state*, not the existence of a decision in a journal. ## 5. Objectives and loops (R19–R22)

This section is the r2 addition that r1 lacked. Vocabulary is fixed first, because three different things are all called “loop” in this codebase (F17) and the panel must never conflate them:

- **Track objective** — work recorded in Track and referenced explicitly (§5.1). Track is the source (R19); the panel and h2a only reference it.
- **h2a objective loop** — the durable h2a store + tick engine + optional supervisor (F11–F14). This is h2a's own loop and the universal fallback (R21).
- **Native CLI loop** — a CLI's in-session self-continuation mechanism (§5.3). It lives inside the agent session; h2a can request and observe it only indirectly.
- **Drumbeat** — external anti-stall relance on `workStatus` (F17). A signal source for the tick engine, displayed as work status, never labelled “loop engaged”.

### 5.1 What “objective” and “engaged” mean, operationally

Track owns no cross-repo objective aggregate (F18), so the panel's objective is a **referenced set**:

- An **objective** is identified by an h2a objective loop's declared refs (F11): one or more `TrackObjectiveRef`s (F18) with at least one `primary`/`target` role, each resolved in its own project's journal of record (§4.3, §5.5). The loop's `goal` text is display text; the refs are the identity. A loop with zero refs is a free-text goal (`explicit-done` policy in the store) — shown as “goal (no Track ref)”, never presented as a Track objective.
- **“Engaged objective” is a Track fact, not a loop artifact (R19; OQ-16).** Track already records commitment: item `disposition` per gate carries a `commitment` gate, `engagementRef` means “a contract exists”, and decisions exist with `--kind orientation|commitment` (F19). r2 defined objectives *through* loops only, so Track-engaged work assigned to a session but with no loop rendered as a silent “candidate” — exactly the case the owner wants alerted (19:05/19:10). This spec therefore does **not** settle the sense of “engaged” alone: **OQ-16** offers (a) non-terminal h2a loop referencing the ref (= r2), (b) non-terminal Track item/WP whose `commitment` gate is `completed` or which carries `engagementRef`, assigned to the session (tier-2 RACI = exact instance), (c) (a) ∪ (b) — recommendation: **(c)**. Until OQ-16 is answered, lots build against (c): the h2a loop stays the *execution* aggregate (the 2026-06-26 model, F18, is unchanged) while Track decides *engagement*; case (b)-without-(a) renders `↻ NO LOOP *` (§5.2) and one L6 action (create-with-refs) resolves it. If the owner answers (a), the `NO LOOP` row and its fixtures leave the spec by amendment — silently keeping (a) while claiming R19 coverage is the r2 error this bullet removes.
- **Active objective (R13):** the objective is engaged (OQ-16 sense) **and** — when it has a loop — the loop is non-terminal (F12) **and** at least one `primary`/`target` ref is not proven terminal-satisfied. Per ref, terminal means: item realization in `done/cancelled/rejected` with the tick mapping's satisfied reading, decision outcome settled, container terminal (F19 test, machine-filtered from full-forest JSON; exact per-kind mapping is the tick rollup's, §5.5). Individually satisfied refs stay visible as satisfied inside a still-active objective. Unresolvable refs (store missing/unreadable, id absent) yield `unknown` — never “satisfied”, and never by themselves “inactive” (F14 posture).
- **Session ↔ objective binding** (“this session has an objective it could pursue”, R20) is a *recorded* relation, resolved in this priority order — never inferred from titles, cwds alone, or open-work counts:
  1. **Loop enrolment:** the loop's `agents[]` contains the session's h2a instance (`h2aInstance`, F11) — set by `h2a loop join` / `h2a_loop_join`. Strongest evidence; carries the agent role.
  2. **Track assignment:** a referenced aggregate (or its `primary`/`target` item) names the session's instance/actor in `accountable` or `responsible[]` (F19).
  3. **Launch binding:** the session was launched for the loop (loop agent launch spec name / launch context recording the loop id where the launcher recorded one). If no surface recorded it, this tier is empty — the panel does not reconstruct it from process argv.
- **Candidate (unbound) objectives:** active Track objectives in the session's workspace(s) with no binding to this session (e.g. an unfilled planned agent slot on a loop whose repos include the session's project, or active `primary` work with no accountable session). Candidates are *listed* (objectives view, §5.5) so R20's “could pursue” is visible, but in v1 they do **not** raise the per-session `*` — only bound-but-not-engaged does (§5.2). Widening the alert to candidates is OQ-9 (recommendation: no — every session in a busy repo would alert permanently).
- A session may be bound to several objectives and an objective to several sessions (multi-agent loops, F11). Per-session display shows each binding; the aggregate per-objective state is §5.5.

### 5.2 The default rule and the explicit per-session state machine (R19/R20)

Owner rule: *bound active objective ⇒ objective loop is the expected state; no bound objective ⇒ no loop expected.* The panel (and, from L2a, the bottom bar for the attached session, §4.4) renders exactly one state per (session, bound objective) pair — collapsed to the worst state on the session row when several bindings exist, expandable to each pair:

| Displayed state | Token (row) | `*` | Meaning (evidence required; §5.4/§5.6) |
|---|---|---|---|
| No objective bound | `no objective` | — | No tier-1/2/3 binding to any active objective. No loop expected (R19 second clause). |
| **Engaged in Track, no loop** | `↻ NO LOOP` | `*` | Track-engaged work bound to the session (OQ-16(b), tier-2 exact instance) with **no h2a loop referencing it**. The R19 default-rule gap in its purest form; one action (L6 create-with-refs) resolves it. Counts as an attention subject (§4.5). |

Rules that keep this table sound:

- **Silence is never “engaged” — and the attestation contract ships in L2a, not L6.** Native engagement needs positive attestation. The contract is a *read/write shape*, so it lands with the read model: an **engagement attestation** is a loop report event whose payload carries `engagement: { mechanism: "native"|"h2a", state: "engaged"|"disengaged", tool, at }` (one additive field on the existing report event, written via `h2a loop report --engagement …` / `h2a_loop_report`; today's `LoopReportInput` has no such field). Stale attestation (older than the loop's `tickMs` × 3, the F13 staleness constant) decays to NOT ENGAGED, not to engaged-forever. Before any attestation exists, a native-capable pair renders `↻ native ?` (no `*`) — without this, L2a would display an explicit-but-wrong `NOT ENGAGED *` for every genuinely-running native loop, the opposite of R20. h2a engagement needs opt-in + attendance, both read-side (F13). L6 keeps only the panel *actions* (§5.4).
- **`*` is reserved to owner-actionable states.** Decision, question, `blocked`/`failed`, `NO LOOP`, `NOT ENGAGED`, `waiting-human`. `unattended`, `stalled`, `degraded` and `frozen` render as words (plus one aggregated header line) and never light the collapsed marker — the same anti-inflation argument OQ-9 applies to candidates.
- **Kill-switch visible.** When `H2A_LOOP_AUTOTICK_OFF` freezes auto-ticking (F13), h2a-engaged rows render `↻ h2a (frozen)` and the objectives header says so — a frozen fleet must not read as per-session faults.
- **Work status stays separate.** Drumbeat `workStatus` (`working/paused/blocked/out-of-tokens`, F17) renders as the session's work token, not merged into the loop token: a session can be `working` with loop NOT ENGAGED (exactly the gap R20 wants visible) or `paused` with loop engaged-native (self-wake pending).
- The state machine is a **read model** in lots L2a/L2b (no panel writes; the only new write shape is the L2a attestation field agents emit). Engagement *actions* that change state are lot L6 (§5.4).

### 5.4 Engagement protocol (lot L6 actions; read model + attestation contract first in L2a/L2b)

The default rule (R19) meets a coded safety rule: auto-ticking is opt-in per loop precisely so that enabling infrastructure does not resurrect every loop at once (F13). This spec resolves the tension as **expected + alerted + one explicit action to engage** — the panel never silently flips `autoTick`, never starts a native loop by typing into a PTY behind the owner's back, and never hides the gap. Whether binding alone should auto-engage is OQ-10 (recommendation: no silent enrolment; see §13).

Engaging a bound (session, objective) pair from the panel (`/a` is answers; loop actions live in the session/objective expander — keys in §9.2) performs, in order:

1. **Ensure the h2a loop exists and is bound.** If the objective has no loop yet, offer creation with the objective's refs pre-filled (`h2a loop create --track <refs>`, F11) — the owner confirms (`Enter`); the panel creates nothing on a bare keystroke. If the session is not enrolled, enrol it (`h2a loop join` semantics: idempotent, conflict = shown error, never overwrite a different recorded enrolment).
2. **Native-first (R21).** If the session's CLI has a native mechanism (§5.3): send the *engage request* — launch-prompt instruction for new sessions, `h2a send` for-info message for running ones (same signed-inbox channel as §7, marked as a loop-engage request carrying loop id, objective refs, and the attestation expected back). The agent itself starts its native loop/goal and attests by `h2a_loop_report` (or the MCP/CLI equivalent) with mechanism `native`. Until attestation arrives the state stays NOT ENGAGED with sub-state text `engage requested <time>` — the request is visible, not counted as engagement.
3. **h2a fallback / choice.** If the CLI has no native mechanism, or the engage request is declined/times out (proposal: no attestation within 2× `tickMs`), or the owner chooses h2a explicitly: offer `loop enable-auto-tick` for that loop (per-loop opt-in, F13) — again `Enter`-confirmed, with the supervisor consequence named in the confirm line (“requires the loop supervisor; currently: attended/unattended”). Enabling opt-in without a running supervisor yields UNATTENDED (§5.2), which is the correct visible outcome, not a failure toast.
4. **Record.** Every step writes through existing surfaces only (loop store events `loop.created/track-linked/agent-joined/auto-tick-enabled`, agent reports; `h2a send` exit evidence shown like §7). The panel adds no second engagement journal; the *mechanism* per agent (`native|h2a`, attested-at) is derived from the latest **engagement attestation** for that agent — the additive `engagement` field on the report event defined in **L2a** (§5.2/§11), not a new file and not an L6 invention. L6's new writes are the panel actions only (create/enrol/engage-request/enable-auto-tick/disengage).
5. **Disengage/stop.** Symmetric explicit actions: stop native (for-info request + attestation decays), disable auto-tick (store write, event), `loop stop` (terminal, human-confirmed). `blocked` recovery stays explicit and CLI-only as the engine already requires (F14) — the panel links to it, never one-key “unblocks”.

Guardrails inherited, not reinvented: human-typing guard + R3 idle gate for any wake injection (F14); single-writer executor lease for ticks (F13); kill-switch supremacy (engaging while frozen records opt-in but renders `frozen`, §5.2); no PTY writes to a session the panel merely observes (F4).

### 5.5 Multi-project objectives at meta-workspace level (R22)

- **Attachment level.** An objective is attached to a **meta-workspace** (panel tab, §4.2) when its refs'/repos' projects intersect that tab's projects, or when any bound session lives in the tab. The objective renders **once** in the tab's objectives list even when it spans several of the tab's projects; if it also touches projects in another tab, it renders once per concerned tab with a `also in <tab>` marker — identity is the loop id, so the two renderings can never diverge into “two objectives”.
- **Per-project citation, no silent copy.** Each ref row in the objective expander cites its source: `repoKey · workspace · aggregateKind/id · track-dir · journal head (short) · resolved status`. Reads are per-ref against that project's **journal of record** (§4.3 — explicit `rightPanel.trackDirs` else main checkout, never a linked-worktree copy, never the session cwd); the panel never copies events between journals, never writes Track except through §7's answer path (writer policy included), and shows `unknown` per ref when that one store is unreadable while other refs still resolve.
- **Aggregate rollup (explicit, worst-first).** Objective-level state = the worst of its refs under this fixed order: `unknown` (any primary/target unresolvable) is *reported alongside*, not averaged away — the row shows `n/m refs resolved`. Satisfaction follows the store's own semantics: refs map to `accepted|done|pending|rejected|blocked|stale|unknown` (tick rollup vocabulary, F14/F15); the objective is *closable* only under the loop's `successCriteria` + `decisionGatePolicy` (F11) evaluated by the tick engine — the panel displays the engine's verdict (§5.6), it does not compute a second closure rule. `decision-gate` refs surface as the blocking decision rows (§4.3) with a back-link to the objective.
- **Per-session state stays per session.** Aggregation never hides a pair state: the objective row shows `↻ 2 engaged · 1 NOT ENGAGED *` style counts over its bound sessions, and expanding lists each (session, state, mechanism, attestation/heartbeat age). A multi-project objective with one neglected project session therefore alerts exactly where R22 requires: per session *and* aggregated.

### 5.6 What is displayed: iteration, last verdict, freshening

Derived read-only from the loop store (F14 — no stored counter exists):

- **Iteration** = count of `loop.tick` events in `events.jsonl` for the loop (dry-run ticks counted and marked `dry` on the last one if applicable). Native-loop internal iterations are not countable from outside (§5.3); for native-engaged pairs the expander shows `h2a ticks: n · native iterations: not observable` rather than inventing a number, plus the agent's last report note/time.
- **Last verdict** = last `loop.tick` outcome + degraded flag + planned action types, with reasons shown in the expander; when the tick engine's fuller plan is needed, `h2a_loop_status`'s last-tick observation is the existing read surface — the panel consumes the same derivation, not a re-implementation of `planLoopTick` in the attach process. No tick ever recorded ⇒ `no tick yet`.
- **Freshening.** The panel snapshot (§11) follows the §11 read-path cadences (registry/host ≤ 1 Hz; Track/loops on `(size, mtime)` change; transcript scan ≤ 1/60 s, expander-only) plus an immediate rebuild after any panel action. File reads are bounded (the bar counter's 64 KiB bounded-read posture, F16) and a torn/oversized `state.json` degrades that loop to `unknown`, never crashes attach. L2a owns the F16 reconciliation so bar `L` and panel loop tokens derive from one vocabulary; until then the panel is the correct surface and the bar counter's possible `L?` is a known, documented limitation — not silently “fixed” by display tricks.

## 6. Track pane (R6/R13)

- **Content.** `track report --status-table` (F21) for a chosen period: `today`, `week`, `month`, `all`, `last-week` (the status-table default), `last-day`, or explicit `--since/--until` — the exact F21 selector set, no panel-invented periods, `--since`/`--period` mutual exclusion preserved in the UI. (`track report --owner-table`, added by merged PR #457, is the ETA-oriented roster view; the pane keeps `--status-table` as its single r3 source because its four sections + period semantics are what R6 names — offering `--owner-table` as a second toggle is a later additive option, not a silent substitute.) The pane renders the four sections in panel width, then the summary block. L0 ships the `/t` view as an explicit “not in L0” placeholder (B1); the real pane is lot L4.
- **Which journal(s) — multi-project correction.** The pane is scoped to the **selected session's workspace by default**, switchable to any project in the current tab, always against that project's **journal of record** (§4.3); each rendering header cites `workspace · track-dir · period · journal revision (events/head short)` (F15/F21). For a multi-project objective (§5.5) the pane offers one report **per concerned project** (tabbed/stacked, each cited) — never a merged cross-journal report, because Track has no cross-repo report semantics to reuse (F18) and inventing one in the panel would create the silent-copy R22 forbids.
- **Summary route (named, no new keys).** The chosen period's report JSON is summarised by a low-cost third-party model **through the existing local gateway only**: model `gemini-3.8-flash` (alias `flash`, F22 catalog) called on the local gateway base URL resolved exactly as the status snapshot resolves it (F22), under a **dedicated gateway client identity** (`h2a-panel-summary:<attach-id>`), never a CLI session's id — otherwise the bar would read `gemini-3.8-flash` as the attached session's own route via `/v1/status/client/<id>`. No provider key in the panel, no direct provider call, no new config file. **Active objectives are rendered deterministically from the report JSON above the summary** (F19-filtered titles/ids, verbatim by construction); the model only narrates *movement in the window* from the recent status. There is **no verbatim must-keep check on model output** (r3: abbreviations/reformulations would fail it constantly and make “summary unavailable” the common case).
- **Enablement & privacy.** Summarisation sends project text to a third-party model via the gateway; therefore it is **opt-in per workspace, default off** (recommendation carried into OQ-7 for owner confirmation; the route itself is not in question). With opt-in off the pane is the raw report only — fully functional, no nagging.
- **Cache & degraded states.** One summary per (workspace, period selector, journal revision `count+head`, F21); a moved journal invalidates. In order: opt-in off → no summary block; gateway posture direct/off or base URL unresolvable → `summary unavailable (gateway off)` + raw report; gateway/model error → `summary unavailable` + raw report. The summary never blocks, delays or overwrites the raw report (deterministic objectives block included), and is labelled as machine-generated, with model id + generation time.

## 7. Asynchronous decisions (R7)

### 7.1 Principle and boundary

A decision answered in the panel is answered **asynchronously** w.r.t. the concerned session: the session is *informed*, never interrupted, never presented with a blocking question by the panel. **OWNER GATE records (2026-11-07 D3) are never answered by `/a`** — their closure condition is “required owner answer in the required session”, stronger than any panel-side check and unobservable from the panel: the row shows `answer in <target session>` and activation jumps to that session; `/a` applies to ordinary decisions only. (r2's weaker “currently blocked natively” condition is removed: the panel cannot observe it, and D3 does not ask it to.)

### 7.2 Answer flow (`/a`, lot L5)

1. Owner selects a decision/question row, then an option (structured dossier) or confirms the outcome (unstructured dossier) — the affordances Track's canevas already advertises (F20). Free-text answers to `qa[]` questions are recorded as dossier QA answers through the existing Track write surface where one exists; where Track offers no QA-answer event, `/a` on a pure question records nothing in Track and only informs the session (step 3) — the row states which case applies before confirming. (L5 verifies the exact Track verb set; inventing a Track event from the panel is forbidden.)
2. **Track records first** (decisions): `track decision select <decisionId> <optionId> [--outcome go|no-go]` against the decision's **journal of record** (§4.3) — never a worktree copy, never cwd-resolved. Track write failure ⇒ nothing is sent, failure shown on the row; the answer exists nowhere else. **Writer policy per workspace (OQ-17):** `direct` (the panel runs `track decision select` against the journal of record) or `delegate` (the panel sends the chosen answer to the declared single writer with `h2a send` and shows `answer delegated to <writer> · deposited`; the row stays pending until the writer records it). Recommendation: per-workspace, with `delegate` → h-cond for h2a, honouring the owner rule “no `.track` writes in PR branches; h-cond is the single writer of the live store”. r2's “same CLI surface any operator would” sentence is removed: the rule governs *who* writes, not which surface is used, and `withFileLock` prevents journal corruption, not a policy breach. In `delegate` mode the panel performs **zero** Track writes.
3. **Then h2a informs:** `h2a send <target> <message>` (F24), marked for-info, carrying decision id + title, chosen option id + title (or QA answer), answer time, and dossier locator (`track focus <id>` / artifact ref / loop id when the decision gates an objective, §5.5). Ordinary signed message body — no new envelope type; a message never proves consent or a native question (owner-gate boundary).
4. **Evidence wording is exact.** `h2a send` exit 0 ⇒ row shows `deposited in inbox · <time>` — **not** “seen” or “applied” (F24). Failure (unknown/ambiguous target, key/inbox error — exit 1/2/3 mapped to their meanings) ⇒ `not sent — <reason>` + retry; the Track record stands, never rolled back, and retry never duplicates the Track event. When the decision gates a loop, the next tick's `route-decision`/verdict (§5.6) is the observable “loop noticed” signal and the objective expander links to it.

### 7.3 Concerned-session resolution (no guessing)

Deterministic, in order: (a) loop `decision-gate` target / gating loop's enrolled agent(s) for that workspace (F11/F14); (b) decision `accountable` / linked item `accountable|responsible` matching exactly one live session instance (F19/F20); (c) exactly one live session in the decision's `workspace`. Zero or several matches at every tier ⇒ Track answer still recorded, row marked `no live session — not sent`, owner picks the target from the session list before retry. Title-substring matching is forbidden. Multi-project decisions resolve per the decision's own workspace (its journal of record), even when the gating objective spans further projects (§5.5).

## 8. Gateway switch (`/gw`) and configuration (`/c`) (R10/R14/R16, lot L7)

### 8.1 What `/gw` can actually switch (F23 correction applied)

`/gw` on the selected session offers **only the levers that exist per session**:

1. **Posture toggle** `gateway ↔ direct` — the recorded launch pin (F22). Takes effect by restarting the same session (§8.2); the pin is re-emitted (`--gw/--no-gw`) exactly as restore does.
2. **Launch model choice** — relaunch with a different `--model` from the gateway catalog/aliases or the CLI's native model ids (F22/F10). The confirm line shows current observed route (`requested→upstream`, F6) vs. the requested new model; the *effective* upstream after restart is whatever the gateway then reports — the panel displays it, never promises it.
3. **Display-only (global) mappings.** PR #462 `modelRewrites` and routing `activeProfile` are gateway-host-global, startup-loaded (F23): the panel *shows* the effective rewrite for the session's last route when the gateway reports one and links to the config/restart procedure (`h2a llm-mesh restart`), but offers **no per-session rewrite editing** in v1. Until PR #462 is merged this block reads `model rewrites: unavailable (PR #462 not merged)` — never a guessed mapping. Making rewrites per-session would be a gateway-host design change; it is OQ-11, not assumed here.

### 8.2 Same-session restart semantics

Applying §8.1.1/§8.1.2 restarts **the same conversation** (R10): verify identity first (native: exact incarnation; tmux-legacy: F25 safety — indeterminate evidence means *do not kill*, show the refusal), stop, relaunch via the per-profile resume argv (F10) with the new pin/model, same cwd/label. **L7 pre-gate (F10):** resume argv is verified per profile against the then-installed binaries before any restart ships; for **agy**, either the two call sites are aligned on `--conversation` (fix outside the panel, dedicated PR) or agy rows show `/gw unavailable — resume argv unverified` — restarting on a guessed flag risks opening a *new* conversation instead of the same one. The panel shows `restarting…` then the new observed `gw`/route state from the snapshot. Hard rules: `Enter` confirmation every time (OQ-12 default); sessions without a resolvable conversation id (attach-live rows, F7/F25), remote/SCW sessions, and dual-host-ambiguous identities show `/gw unavailable — <reason>`; no code path force-kills; restarting the *attached* session from its own panel first returns focus/geometry cleanly — **observer-survives vs. re-attach is OQ-21**, not an L7 implementer's pick (silently detaching the owner is a failure either way). Loop bindings survive restart (enrolment is by instance, F11) but native engagement must be re-attested (§5.3) — the row shows NOT ENGAGED until it is, which is correct, not a bug to smooth over.

### 8.3 `/c` configuration

Panel-local settings only: width (20–60, applied next open), opener key (`F12` default, `F9` alternative — §9), summary opt-in per workspace (§6), sub-pane fraction (§4.3). Persisted in the same remote config file the bar flag already lives in (F5 shape: `rightPanel: { enabled, width, opener?, … }`; env still wins over config per B2 precedence). `/c` never edits gateway-host config (`llm-mesh.json`), Track data, or loop policy — those keep their own surfaces (§8.1.3, §5.4).

### 9.2 Keyboard scheme (owner grammar kept, opener corrected)

- **Capture order in `runAttach` (new, next to F2):** (1) `DETACH_BYTE` wins over everything, in any focus — detach is never shadowed by the panel; (2) opener sequence (`F12`/`F9`, incl. split-sequence buffering per B1: a partial opener prefix is held, never leaked to the CLI; a held prefix that completes as something else is forwarded whole); (3) SGR mouse sequences (§9.3); (4) in panel focus, panel grammar; (5) otherwise forward byte-identical. With the feature flag off, steps 2–4 do not exist.
- **Opener:** `F12` toggles open/close from any focus (B1). Opening moves input focus to the panel; closing returns focus to the CLI. `Esc` in panel focus returns focus to the CLI **without closing** (B1 — the panel stays visible as a read-only board while the owner types in the CLI; F12 or a panel click refocuses/closes per §9.3). While the CLI has focus, *only* the opener and detach byte are captured; while the panel has focus, nothing is forwarded to the child (its screen stays live behind).
- **In-panel grammar = owner's, unchanged (R16), as a byte-stream state machine.** Human typing delivers one key per read, so whole-chunk comparison (`input === "/s"`, as shipped in #465) never fires at a real keyboard. Normative: `/` opens a one-line prompt in the panel header accepting `s d t a c gw`; completion on the second key (or `Enter` for `gw`), `Esc` cancels, unknown ⇒ `unknown: /x` shown, **no timeout**. Commands: `/s` sessions (default view), `/d` decisions/questions, `/t` Track, `/a` answer (§7, lot L5 — before L5 it renders its lot marker, never a dead key), `/gw` (§8, L7), `/c` (§8.3, L7). `Tab` next meta-workspace tab, `Shift+Tab` (`CSI Z`, distinguishable in panel focus) previous. Row navigation: `↑/↓` (and `j/k` as aliases *inside panel focus only*, where they cannot collide), `Enter` activate/confirm, `→/←` or `Space` expand/collapse (`delegated`, `objective/loop`, `restorable`). Loop actions (§5.4, L6) live in the expanded row: `e` engage.., `x` disengage/stop.. — both open a confirm line; **no state-changing action fires without `Enter` confirmation**, and destructive ones (restart, stop, send) always confirm. Free text is accepted only where a field is open (`/a` answer text); stray typing in panel focus is consumed and shown as ignored, never forwarded by accident.
- **Bytes stay bytes.** Input is handled as bytes end-to-end; forwarded bytes are **never decoded/re-encoded** (#465 decodes each chunk as UTF-8 and re-encodes — a multibyte character split across chunks becomes U+FFFD, violating “reach the child unmodified”). When the child has pushed kitty flags (relayed outward, F3/K2), the panel also accepts the kitty forms of Esc, Tab, arrows and F12 (`CSI 27 u` etc.). **Bracketed paste:** opener and mouse-sequence detection is suspended between `ESC[200~` and `ESC[201~` while the child has mode 2004 on, so pasted text containing `ESC[24~` or `ESC[<…M` reaches the child as text. Arrow keys arrive as `CSI A..D` or, under child DECCKM, `SS3 A..D` (Annex B) — both forms navigate.
- **Equivalence rule:** everything clickable is keyboard-reachable and vice versa (R15 is *in addition to* the keyboard). Lot acceptance includes a keyboard-only walkthrough and a mouse-only walkthrough of the same actions.

### 9.3 Mouse contract (R15 — every panel and bottom-bar element clickable)

- **Reporting mode — h2a owns the outer mouse mode while the feature is on.** Child output is relayed to the outer terminal today, so a child's own `?1000l`/`?1006l` would cut h2a's tracking (or drop the terminal to X10, whose `ESC [ M …` bytes the SGR parser cannot read and which would reach the CLI as typing), and its `?1002h`/`?1003h` would produce motion h2a never asked for. Normative: child DECSET/DECRST for `9/1000/1002/1003/1005/1006/1015/1016` are **recorded by `TerminalModeTracker` and consumed from the relayed output**; the outer terminal stays at `?1000h ?1006h` for the *whole attach* — open **and collapsed** (collapsed clicks must be deliverable; #465 enables mouse only while open, L0.5 fixes it) — plus `?1002h`/`?1003h` **only while the child requests them**; events are transcoded to the child's requested encoding; **closing the panel never emits `?1000l`**; detach/exit re-emits the child's recorded set. Trade-offs stated plainly: with the feature on, outer-terminal text selection needs **Shift+drag** (K5) **and the wheel no longer scrolls VTE scrollback in the CLI zone unless the child subscribed to it** — for a normal-screen unsubscribed CLI the wheel would do nothing while the feature is on (status `unverified` until L0.5.6 measures it under the bar's DECSTBM region; OQ-5 carries this cost, incl. option (c) open-only). With the feature off, mouse behaviour is byte-identical to today.
- **Parsing.** Incremental SGR parser (`ESC [< b ; x ; y M/m`) over the input stream, split-sequence safe (incomplete tail buffered, B3); malformed/oversized sequences are dropped as panel input and never forwarded as garbage to the child. Press (`M`) acts; release (`m`) is consumed without acting (except drag-end for future use); motion reports are not requested (`1002/1003` are not enabled by h2a on the outer terminal).
- **Routing by coordinates (B3 zones, 1-based `x,y` as reported):**
  - `x > childCols` and `y < rows` (panel or marker column): **panel zone** — h2a handles it, nothing forwarded. Hit-testing is by rendered cell ranges (tab label spans on row 1 select *that* tab — L0's interim “tab-row click cycles” behaviour (B3) is tightened to direct selection in L1; row hits select, second click/`Enter`-equivalent double-click activates (dossier/sub-pane, expander toggle on the `▸` cell)). Clicking the collapsed marker column toggles the panel open.
  - `y = rows` (bottom-bar row, **bar active only** — §4.1 bar-inactive case routes this row to child/panel): complete token → action map (R15 covers *every* bar element): marker span toggles the panel; `J` ⇒ delegated expander of the attached session; `I` ⇒ `/d` view; `L` ⇒ loop expander (L2a); cli/session/role span ⇒ select the attached session's row; delegated-names span ⇒ select that delegated session's parent row (L1+); gateway span ⇒ open the panel with the **attached** session selected and its `/gw` confirm line pre-opened (the bar's gw segment describes the attached session; `/gw` still needs its `Enter` confirm). Bar clicks never reach the CLI (the row is reserved, F1). The gateway rewrite display (PR #462) lives in the bar's route token itself (`requested→target (rw)`) once #462 merges — owner: “la partie gw … comme en bas dans le bandeau” — not only inside the panel's `/gw` block.
  - `x ≤ childCols` and `y < rows`: **CLI zone** — forwarded to the child **only if the child itself enabled mouse tracking** (F3 accessor: any of `1000/1002/1003` on). Forwarding transcodes to the child's negotiated encoding: verbatim SGR bytes when the child enabled `1006`; re-encoded X10/`1015` forms otherwise; event classes the child did not subscribe to (e.g. wheel without the corresponding mode, motion) are dropped, not approximated. Coordinates need no translation (panel is right of the child area, child origin stays at 1,1; the reserved bottom row is already outside the child's rows). When the child has no mouse tracking, CLI-zone clicks are consumed (they belong to h2a's reporting session) — the owner's selection path is Shift+drag, next bullet.
  - **Shift-modified events** (button code bit 4): `native-selection` — never acted on by the panel, never forwarded; combined with VTE's emulator-level Shift bypass (K5) this keeps native text selection working. (Where VTE swallows the Shift+drag entirely at emulator level, no event arrives — also correct.)
  - **Wheel** (buttons 64/65): in panel/marker zone, scrolls the panel list (and the sub-pane when the pointer is over it) by 3 rows per notch; in CLI zone, forwarded under the same child-subscription rule as clicks; over the bottom bar, ignored.
- **Focus on click.** A panel-zone click while the CLI has focus selects *and* gives the panel keyboard focus (so `/a` etc. work immediately); `Esc` returns keyboard focus without closing (§9.2). Clicking in the CLI zone returns keyboard focus to the CLI (forwarding still governed by child mouse state — focus and mouse-forwarding are independent axes and the spec keeps them so).

## 10. Accessibility (symbol + word first; colour never alone, R12)

The 2026-11-17 verbatim names no colour-vision condition (r3: r2's “owner colour-blindness” was unsourced and is withdrawn) — the design rule below stands on R12 itself (“colour **plus** `*`”): colour is never the only channel. Every state is **symbol + colour + `*`/word**:

| State | Symbol | `*` | Notes |
|---|---|---|---|
| running / working | `●` | — | |
| idle / waiting input | `○` | — | |
| waiting (CI/agent/tick) | `◐` | — | loop `waiting-agent` reuses this + token word (§5.2) |
| paused | `⏸` | — | wide glyph — L1 verifies column accounting with wide/ambiguous-width glyphs (F6 width function) and falls back to `\|\|` if a fixture terminal disagrees |
| blocked / failed | `✖` | `*` when actionable | loop `blocked/failed` always `*` (§5.2) |
| decision pending | `◆` | `*` while pending; **none when deferred** | deferral is the owner's own postponement (§4.5) |
| question unanswered | `?` (+ word on selection) | `*` always | glyph `?` means *question* only |
| loop NO LOOP / NOT ENGAGED | `↻` + words `NO LOOP` / `NOT ENGAGED` | `*` always | words, not hue, carry the R20 alert |
| loop native unverified / unattended / stalled | `↻` + words `native ?` / `unattended` / `stalled` | — | no `*` (§5.2 anti-inflation rule) |
| unknown / degraded | `·` + literal word `unknown` | — | distinct glyph from question — `?` no longer does double duty (r3; distinction must not ride on a muted hue alone). The collapsed *marker column* keeps `?` for “panel state unreadable” (§4.5) — a different surface with one column and no word room; the open panel header spells it `unknown`. |

Rules: `*` ⇔ owner attention required *and actionable now* (decision pending, question, actionable block, `NO LOOP`/`NOT ENGAGED` loop gap) — it is the primary scan signal; selection uses reverse video, not a hue change; the lit marker pairs background with `*`; panel and bottom bar share one symbol vocabulary (§4.4/§5.6) so the two reserved areas cannot disagree; monochrome/`NO_COLOR` loses nothing (symbols, `*`, words carry full state); all glyphs must be width-stable under the existing display-column accounting (F6) — a glyph that breaks column math is replaced, not padded around.

Loops: one canonical shared read module (types, status sets, `loopAttendance`, last `loop.tick`), or a vendored copy guarded by a sync test (the `agy-claude-vendor-sync.test.ts` pattern) — never a third hand copy. Cadences: registry + host views ≤ 1 Hz; transcript scan ≤ once per 60 s and only for the “restorable” expander (`discoverSessions` stats/reads every transcript under `~/.claude/projects/*` and `~/.codex/sessions/**` — it must not run at bar cadence in every attach); Track and loops on file change. Budgets (L0.5 acceptance): snapshot build < 50 ms p95 over a 50-session / 3-journal fixture, and no added key-echo latency > 5 ms during a refresh.
