Analyse indépendante, 19 octobre 2026 — incidents PTY A, B et demande C

Les défauts ont un point commun : h2a confond encore plusieurs durées de vie et plusieurs droits. Un PTY peut rester vivant après la mort du CLI ; une fenêtre peut rester ouverte sans que l’humain écrive ; une enveloppe peut être livrée sans que son destinataire soit réveillé ; un paquet peut être installé sans que le processus résident ait chargé son code. Corriger ces distinctions est nécessaire pour restaurer les sessions et superviser les délégations de façon fiable.

La PR #375 est un capital important pour la continuité pendant les upgrades. Elle ne résout ni le réveil d’un PTY attaché, ni la reprise d’un CLI mort dans son shell persistant, ni la classification des sessions restaurables. Elle ne doit pas être présentée comme le correctif global de ces incidents.

**A1 — le JSON illisible est produit délibérément par les adaptateurs de sortie.** `H/src/cli.ts:1878–1918` appelle `performAutoUpgrade`, puis `convergeAfterExplicitUpgrade`, puis imprime `JSON.stringify(...)` dans tous les cas. `H/src/hosts/upgrade-equipment.ts:16–22` exécute `doctor --repair` et stocke `child.stdout` dans `result`, `child.stderr` dans `diagnostic`. Un rapport JSON de manifeste devient donc une chaîne JSON à l’intérieur d’un autre JSON : guillemets, nouvelles lignes et autres échappements deviennent visibles. Les SHA, fichiers sélectionnés et sources appartiennent à un rapport machine, pas au compte rendu par défaut.

Le message « already current or registry unreachable » n’est pas seulement mal présenté : il confond deux connaissances différentes. `H/src/runtime/upgrade/index.ts:1090–1109` produit `already-current` lorsque la vérification n’indique pas d’upgrade ou n’a pas de dernière version. De plus, `cmdUpgrade` renvoie un succès pour `upgraded`/`already-current` sans faire de `hosts.ok === false` un résultat partiel visible. Il faut corriger le modèle de résultat autant que son rendu.

**A2 — `running` est la vie du conteneur terminal.** `R/src/tmux.ts:121–131` définit `LOCAL_WRAPPER` : exécution du CLI, message de sortie, puis `exec /bin/bash -l`. `R/src/native-host.ts:350–396` réutilise exactement ce wrapper pour le PTY natif. Le processus terminal demeure donc en état `running` alors que l’application attendue a fini. Le type exposé `NativeTerminalSessionState`, dans `R/src/native-terminal/host.ts:567–590`, contient le PID terminal, son état et le contrôleur ; il n’expose pas un cycle de vie indépendant du CLI.

Restore perd cette distinction dès `R/src/restore.ts:494–508` : l’inventaire conserve les sessions `status === "running"` et projette essentiellement leur nom et `controlled`. `R/src/launch-layout.ts:269–305` ignore une session contrôlée et rattache une session non contrôlée. Aucun de ces chemins ne constate « le CLI a quitté, le shell est disponible » et ne lance le resume du CLI. Un PTY actif dans la capture du propriétaire est parfaitement compatible avec ce défaut. Si l’ancien host n’expose pas `controlled`, la branche `:282–288` refuse aussi de décider et propose un attach manuel.

Le compte rendu aggrave l’incident : `restore.ts:1145–1169` compte les onglets planifiés, ignore le résultat `{opened, skippedLive}` de `launchLayout`, et renvoie `total`. `R/src/index.ts:10007–10015` transforme ce total en « onglet(s) relancé(s) ». Même `opened`, à `launch-layout.ts:423–432`, ne prouve que la demande de lancement de `gnome-terminal`, pas la reprise du CLI. On peut donc annoncer une restauration sans avoir redémarré une seule application.

La coexistence ancien host/nouveaux clients est un facteur supplémentaire à diagnostiquer, pas une preuve automatique de la cause de chaque session manquante. Le message de reconnexion de `R/src/native-terminal/op.ts:618–665` est générique : timeout, connexion, identité ou requête peuvent le déclencher. Le brief ne contient pas l’erreur sous-jacente permettant d’attribuer chaque boucle à une incompatibilité de version. Le défaut certain est l’absence de convergence explicite et de diagnostic de capacités chargées.

**A3 — ce sont des réponses au protocole du terminal, pas du texte du CLI.** `DCS >|VTE(...) ST`, `CSI ?...c` et `CSI ?2026;4$y`/`?1016;4$y` correspondent aux réponses d’identification/capacités/modes du terminal. Le chemin causal est visible :

1. `R/src/native-terminal/host.ts:1025–1048` stocke la sortie du PTY dans le replay. Il répond lui-même à `ESC[6n` par `ESC[1;1R`, mais laisse aussi passer la requête dans le replay. Cette famille peut donc avoir deux répondants lorsque le terminal extérieur est attaché.
2. `R/src/native-terminal/replay-buffer.ts:72–84` conserve les octets de sortie, y compris les requêtes. `op.ts:590–591` commence un nouvel attach à `seq = 0`, puis `:674–690` relaie les chunks vers le terminal extérieur. Une ancienne requête rejouée peut provoquer une nouvelle réponse.
3. `op.ts:529–548`, puis `:499–518`, transmettent le stdin à `client.write` sans classification des réponses. `host.ts:1234–1240` écrit ces données au PTY courant et les compte comme activité humaine si le bail est humain.
4. Après le CLI, le consommateur de cette entrée est le shell du wrapper. Une réponse tardive ou provoquée par le replay atteint donc readline et peut devenir visible dans la ligne de commande.

Le marqueur `OSC 777;h2a-reset`, `TerminalResetRelay` et `TerminalModeTracker` constituent du capital à conserver. Ils désactivent des modes introduits par l’application, notamment clavier/focus/souris/écran alternatif (`R/src/native-terminal/terminal-modes.ts:25–115`). Ils ne représentent pas les requêtes en attente et ne filtrent pas les réponses entrantes. Les tests fonctionnels actuels `terminal-modes.functional.test.ts:278–300` vérifient le nettoyage des modes et les relances manuelles ; ils ne simulent pas le terminal répondant tardivement aux requêtes du CLI. Répéter un reset ou ajouter seulement un délai ne ferme pas cette voie.

L’occurrence exacte peut venir du replay, d’une réponse tardive sans reconnect, ou des deux. Cette distinction demande une reproduction isolée qui enregistre les deux directions du protocole ; elle n’autorise pas à rejouer l’expérience dans les terminaux du propriétaire.

**A4 — il ne faut pas réinventer un filtre déjà présent ; il faut fermer ses exceptions.** `R/src/restore.ts:301–318` rejette `endedAt` et `role === "job"`, honore une classe explicite, puis classe une ligne historique comme humaine si elle possède un transcript Claude/Codex ou une session tmux correspondante. `registrySessions`, à `:618–622`, applique ce filtre. Les découvertes par scan sont bien marquées `unclassified`, puis exclues à `:1095–1097`. Affirmer que restore restaure aujourd’hui tous les scans ou tous les jobs serait faux.

Les voies encore ouvertes sont précises :

- Une ancienne délégation sans `sessionClass` ni `role:job` peut avoir un vrai transcript ; `hasLegacyTranscript` la promeut en `human`. La preuve établit une conversation, pas son rôle humain.
- Une session explicitement `human` reste admissible même si elle porte une provenance de délégation : `deriveLegacySessionClass` n’inspecte ni `delegationOrigin` ni `delegatorInstance`, pourtant présents dans `R/src/registry.ts:1660–1663` et persistés à `:1686–1693`.
- Le lancement interactif ordinaire dérive la classe de `background`, `headless` et `attachedTerminal` (`R/src/index.ts:6524–6528`). Une revue déléguée lancée par le chemin ordinaire avec fenêtre peut donc être marquée humaine. Une fenêtre est une modalité d’accès, pas une intention de restauration.
- Les tabs remote viennent directement de toutes les sessions retournées par `listRemoteSessions` (`R/src/index.ts:9976–9984`), sous la forme `{id,label,cwd}`. Ce chemin ne porte pas de classe humaine/job et ne passe pas le filtre local.

Le hook actuel est déjà prudent : `R/src/enroll.ts:148–159` n’enrôle pas comme humaine une session sans marqueur ; `REMOTE_JOB_ID` impose `background`. L’incident n’est donc pas démontré comme un nouveau hook qui oublierait ce garde. Il faut tester les lignes historiques, les chemins de lancement secondaires et le chemin remote. Sans les lignes des instances concernées, je ne choisis pas arbitrairement l’une de ces trois provenances pour l’incident réel.

**A5 — « deux instances sur la même session » doit être relié aux identifiants avant de supprimer quoi que ce soit.** Il existe au moins quatre objets : conversation fournisseur, instance h2a pérenne, incarnation du PTY, connexion MCP/présence. Un label `i-cond` peut être partagé par plusieurs objets. Deux lignes de présence ne prouvent pas deux CLI écrivains ; deux contrôleurs interdits ne prouvent pas une unicité de conversation.

Des protections existent : déduplication des resumes par UUID (`R/src/restore.ts:729–760`), rapprochement run/hook (`:406–473`), claim atomique de reprise (`R/src/relaunch.ts:100–173`, appelé par `R/src/index.ts:6360–6367`), garde de conversation (`index.ts:6480–6494`), résolution refusant plusieurs owners de même nom (`R/src/native-terminal/fleet.ts:45–53`). Elles ne doivent pas être affaiblies pour « faire marcher restore ».

Une lacune native concrète demeure dans `R/src/conv-guard.ts:59–82` : `ownerFromEntry` ne traite comme terminal vérifiable que `local-tmux`. Une ligne `local-native` passe dans la branche générique et devient `suspect` lorsqu’elle n’a pas de `pid`, même si `isLive` vient de confirmer le PTY par son nom. `guardConvWriters`, à `:216–222`, permet le lancement lorsqu’il n’y a que des suspects. Or `enrollFromRun` autorise les lignes sans PID et le chemin de reprise à `R/src/index.ts:6018–6050` ne retient que `name` du lancement et ne transmet pas son PID à l’enrôlement. À l’inverse, le verbe natif `relaunch`, à `:9123–9133`, transmet bien le PID lorsqu’il est disponible. Un resume ultérieur sous un autre nom peut donc passer le contrôle de nom et ne rencontrer qu’un avertissement sur la même conversation. Le claim court sérialise deux lancements concurrents mais ne protège plus après l’enrôlement et sa libération (`index.ts:6985–6987`). C’est un contre-exemple à transformer en RED ; ce n’est pas encore l’attribution forensique du doublon `i-cond`.

Deux autres différences comptent : `mergeDiscovered` conserve séparément toutes les lignes attach-only à `sid` vide (`restore.ts:741–744`), et `H/src/runtime/mcp/sessions.ts:126–155` ne refuse qu’un `sessionId` déjà présent dans sa propre map ; il génère sinon un nouveau `sess:*`. Plusieurs connexions MCP d’une même instance peuvent donc produire plusieurs présences. Le binding pérenne, lui, utilise `(host, providerSessionId)` avec preuve de possession (`H/src/runtime/identity/bindings.ts:5–25,113–121`). Un échec de possession peut produire une nouvelle identité ; enlever ce contrôle serait une mauvaise correction du doublon.

Pour attribuer A5, le conducteur devra fournir un petit relevé déjà autorisé ou anonymisé des deux lignes : instance complète, providerSessionId, sessionId de présence, PTY, socket/génération/incarnation, PID et naissance, provenance de lancement. Aucun relevé du propriétaire n’est effectué ici. Le correctif peut déjà fermer le contre-exemple natif, grouper les connexions dans la vue et rendre les conflits explicites ; il ne doit pas tuer automatiquement l’une des deux occurrences sur la seule base du nom.

**B. Relance : l’endroit et le moment du conseil sont erronés.** La commande imprimée par le wrapper est `h2a run ... -r ...`, construite par `localRelaunchCommand` (`R/src/tmux.ts:181–194`). Elle est imprimée à `:130`, immédiatement après la sortie du CLI, juste avant le shell persistant. Le commentaire lui-même prescrit ce moment erroné. `R/src/native-host.ts:388–393` fournit cette commande au wrapper natif. La reconstruction n’échappe pas non plus les chemins/labels et ne représente pas toutes les options conservées de lancement.

Dans ce shell, l’action correcte est le resume de l’application, par exemple `claude --resume <UUID confirmé>` ou le tableau d’arguments de resume du profil. Le conseil extérieur recrée un h2a autour d’un h2a déjà vivant : il rencontre les gardes d’identité ou le contrôleur déjà détenu. Le code ne démontre pas une interdiction universelle de toute commande h2a exécutée dans h2a ; le problème est la recréation de cette même session.

Il faut également distinguer le libellé imprimé du vrai verbe `h2a relaunch`. Le chemin natif exact de ce verbe existe (`R/src/index.ts:9009–9139`) : il vérifie, puis appelle `killNativeSessionTree`, crée un nouveau PTY et réenrôle. Ce n’est pas une reprise du CLI dans le shell existant. Lancé depuis la cible qu’il tue, il peut supprimer son propre contexte avant la fin de la reprise. Le mode `--all` reste tmux-only. Sous tmux, le chemin historique `relaunchInSession` écrit la commande de resume directement au shell existant (`R/src/tmux.ts:2378–2387`). Cette différence fonctionnelle doit être corrigée, pas cachée derrière un changement de texte.

Le contrat voulu par B est déjà clair : sortie du CLI → shell propre et conseil de resume du CLI ; sortie effective du PTY, typiquement le second Ctrl-D → retour dans le terminal extérieur et conseil h2a. Un Ctrl-\\ de détachement ne signifie pas que le PTY est fini : son conseil doit proposer un attach. Une perte de transport non résolue ne doit pas être présentée comme une fin de session.

**C. Send/sendmessage, wake et supervision des délégations.** Demande ajoutée du propriétaire, conservée verbatim : « il faut des méthode pour superviser les pty délégués donc il faut ces méthodes d'injection, comme les sendmessage qui reposent la dessus j'imagine (historiquement c'était la méthode sendmessage en tmux, qui ne fonctionne toujours plus depuis le switch a pty) » — suivi `01M5A9G9ESXD5RM0T7K0DJ12QM`. Les incidents A/B sont associés dans le brief à `01M5A9CAZ75BNCP73B0JCA9H4J` et `01M5A9CGQJV44H4XYK4XCT8TPV`, WP5. Aucun de ces éléments n’est modifié ici.

La fonction actuelle `sendMessage` et l’outil MCP `h2a_send` transportent une enveloppe signée. Le code courant ne contient pas de primitive h2a distincte nommée littéralement `sendmessage` ; le terme du propriétaire désigne ici la fonction attendue d’envoi/réveil, pas une preuve sur un nom d’API historique précis.

| Étape | Sous tmux | Sous PTY natif aujourd’hui |
|---|---|---|
| Dépôt du message | Enveloppe signée dans l’inbox du destinataire. | Même contrat local ; backend cluster-mesh également disponible. |
| Détection | Le dispatcher MCP voit l’inbox non vide et rappelle le wake à chaque tick. | Même boucle, si le MCP de la cible est activé et son wake armé. |
| Cible | Contexte tmux, souvent hérité de `TMUX_PANE`; `tmuxTarget` choisit la pane exacte. | Le sidecar publie `H2A_NATIVE_TARGET_SESSION` et `H2A_NATIVE_PTY_SESSION` pour viser le PTY principal, pas sa propre session `.h2a`. |
| Injection du wake | `localTmuxDriver` → `tmuxSendSubmit` → `tmux send-keys -t <pane> -l <texte>`, puis deux commandes Enter séparées. | `nativePtyBackchannelDriver` → `op.js drive --target ... --b64 ...` → résolution du registre/owner → acquisition automation conditionnelle → `write(texte + CR)`. |
| Fenêtre attachée | Le serveur tmux peut injecter tout en gardant son client attaché. Un garde temporel évite l’activité récente, mais est fail-open si sa sonde échoue. | L’attach conserve un contrôleur `human`. L’automatisation est refusée tant que ce contrôleur existe, indépendamment de son inactivité. |
| Texte arbitraire | Les chemins de prompt savent utiliser load-buffer/paste-buffer, avec bracketed paste pour un bloc. | `write`, `paste`, `enter` existent dans op.js, mais réclament chacun un contrôleur exclusif. `drive` n’accepte qu’une ligne sans contrôles. |

Références : `H/src/runtime/send.ts:118–236,249–280` ; `H/src/runtime/mcp/handlers.ts:338–363` ; `H/src/runtime/mcp/notifications.ts:198–216` ; `H/src/runtime/drive/inbox-wake.ts:43–75` ; `H/src/runtime/drive/index.ts:509–532,755–773` ; `H/src/runtime/drumbeat/relaunchers.ts:133–185` ; `H/src/cli.ts:2092–2169,3809–3861` ; `R/src/native-host.ts:690–697` ; `R/src/native-terminal/op.ts:858–931`.

Le texte injecté n’est pas le corps du message original. `H/src/wake.ts:46–57` construit une notification visible `[h2a-wake ...]` invitant le CLI à exécuter `/h2a receive`. `inbox-wake.ts:55–61` la signe avec l’identité de la cible, de cette instance vers elle-même ; seul le transport remplace éventuellement la cible pérenne par le nom volatil du PTY principal. La chaîne attendue est donc dépôt signé → détection par le sidecar → soumission du wake au prompt → lecture de l’inbox par l’agent. Sous tmux, send-keys assurait cette soumission tout en conservant la fenêtre attachée ; sous PTY, le verrou de contrôleur coupe cette étape.

Le point de blocage est exact : `op.ts:571–575` prend le bail humain pour toute la durée de l’attach ; `host.ts:1206–1207` refuse l’automatisation dès qu’un contrôleur existe. Le contrôle des quatre secondes n’arrive qu’après cette condition. `H2A_WAKE_DEFER_ACTIVITY_MS=0` ne permet donc pas d’injecter dans une fenêtre attachée. `write/paste/enter` échouent de la même manière via `withController`, `op.ts:227–236`. Les appels primitifs sans provenance explicite sont en outre comptés comme humains, ce qui peut retarder un drive ultérieur après une opération d’automatisation.

Le wake conserve les messages comme frais tant que le driver renvoie faux (`inbox-wake.ts:71–74`), mais `nativePtyBackchannelDriver` réduit `deferred` à `false` et journalise seulement « failed » (`cli.ts:3840–3843`). `op.ts:890–892` confond dans `deferred` tous les échecs d’acquisition, dont un ancien host ne comprenant pas la méthode. L’utilisateur n’obtient donc ni motif exploitable ni délai/reçu de reprise. Au redémarrage du handler, l’inbox existante est entièrement ajoutée à `seen` (`inbox-wake.ts:45–46`) : un wake différé avant le redémarrage peut ne plus être retenté ensuite. Cette dernière perte concerne la notification, pas l’enveloppe durable.

Le succès de `send` ne prouve donc pas le réveil ni la lecture. Pour MCP, `requireLive:true` vérifie une présence dont le détenteur existe (`send.ts:99–109,175–179`) ; un sidecar vivant ne prouve pas que le CLI est encore là. Le défaut A2 peut ainsi se cumuler avec C : inbox livrée, MCP présent, shell en attente, aucun CLI actif.

L’autorité et l’injection sont aussi séparées. `authorizeDrive` et les signatures existent (`H/src/runtime/drive/index.ts:246–261,339–423`) : self-drive, relation conductor/principal, mandat dans un scope partagé ou consentement. Mais `op.js` reçoit des octets et une cible ; le chemin brut `write/paste` ne valide pas un mandat du propriétaire, et `drive --id` peut sélectionner une session sans résolution du destinataire pérenne. Le socket et le bail constituent une autorité de transport local, pas une preuve d’autorisation agent→PTY délégué. La nouvelle méthode publique doit préserver la vérification métier jusqu’au point d’application et produire une trace d’effet. Elle ne doit pas se résumer à documenter un appel direct à `dist/native-terminal/op.js`.

Les tests existants expliquent pourquoi le manque a pu passer : `R/src/native-terminal/drive.functional.test.ts:93–316` prouve l’envoi vers un vrai PTY et le refus après activité humaine ; le bail humain est relâché avant la tentative. `H/test/pty-native-messaging.test.js:150–192,297–341` utilise un vrai openpty recevant des octets dans un programme Node ; cela prouve l’inbox et la ligne signée, pas la soumission dans un vrai Claude/Codex avec fenêtre attachée. Ces preuves restent utiles, mais elles ne qualifient pas le parcours signalé par le propriétaire.

**D. Comportements cibles et texte de spécification proposé.** Les exigences du propriétaire sont acquises : sortie lisible dans sa langue, exclusion des délégations de restore, absence de doublon, injection supervisable avec fenêtre, respect de la frappe humaine et bon moment du conseil de relance. Les modalités ci-dessous sont des propositions d’implémentation, pas de nouvelles décisions attribuées au propriétaire.

La restauration doit décider sur deux axes séparés, puis rendre un résultat observé :

| PTY / application observés | Action cible de restore |
|---|---|
| CLI vivant, fenêtre déjà visible | Conserver le CLI ; compter « déjà actif ». |
| CLI vivant, aucune vue | Rattacher une vue ; compter « rattaché » après confirmation. |
| PTY vivant, CLI terminé, shell géré disponible, UUID confirmé | Reprendre le CLI dans ce même PTY par une opération autorisée ; vérifier sa nouvelle incarnation. La fenêtre peut rester attachée. |
| PTY vivant, autre programme ou saisie humaine en cours | Différer avec motif ; ne pas injecter une commande de shell. |
| PTY absent avec preuve, conversation reprenable | Réserver l’identité, créer un PTY, reprendre la conversation, confirmer le CLI. |
| Host inconnu, session ambiguë, UUID non résolu ou absence de capacité | Conserver l’état, signaler précisément ce qui manque ; aucun succès inventé. |
| Délégation/job/sidecar, quelle que soit sa visibilité | Exclure du restore humain ; conserver l’accès par la supervision des délégations. |

Le signal de cycle de vie doit identifier l’application attendue et sa naissance, distinctes de celles du wrapper/PTY. Une déduction par faible CPU, nom du processus parent, titre de fenêtre ou simple silence n’est pas suffisante. Une reprise dans le shell doit être liée à une transition gérée vers ce shell et à une commande de resume structurée du profil. Une opération dédiée du wrapper/superviseur avec reçu est préférable à une phrase libre tapée dans un shell supposé vide. Une session historique ne fournissant pas cette preuve doit être annoncée comme non qualifiée pour la reprise automatique.

Proposition normative, en anglais :

> The runtime MUST report terminal lifetime, application lifetime, human input ownership and view attachment as separate states. An unknown observation MUST remain unknown. Restore MUST report per-session observed outcomes: already-active, attached, resumed, excluded, deferred or failed. Planning a tab, spawning a terminal window, or observing a live wrapper MUST NOT count as resuming an application.
>
> A resume operation MUST bind to the exact provider conversation and terminal/application incarnation. It MUST refuse a second live application writer and MUST revalidate its reservation at the application start boundary. A managed shell may resume its application in the existing PTY only through a supported, authorized operation. The current human draft and any unrelated foreground program MUST remain intact.
>
> Default restore MUST include only positively classified primary human sessions. Delegation provenance MUST exclude a session even when it has a visible terminal or a transcript. Unclassified legacy sessions MUST be reported separately and MUST NOT be silently promoted from transcript existence. Views and MCP connections for the same application MUST be grouped without concealing competing application writers.
>
> On application exit, the persistent PTY may show the verified application resume command. An h2a session recreation hint MUST be emitted by the outer launcher/attach client only after observed terminal termination and terminal cleanup. Detach and unproven transport loss MUST produce distinct guidance. Commands MUST preserve the resolved conversation, workspace and applicable launch options, with correct argument quoting.

Pour la supervision, étendre un service commun appelé par les surfaces CLI/MCP et par les drivers existants. Les noms ci-dessous sont des opérations proposées, pas des commandes déjà disponibles :

| Opération proposée | Effet et preuve attendus |
|---|---|
| `inspect` | Instance pérenne, conversation, parent/délégant, classe, owner/génération/incarnation, version installée/chargée, état CLI, vues, saisie humaine, demandes en attente et raisons de report. |
| `capture` / `watch` | Vue écran et flux avec curseur, limite et indication de trou de replay ; lecture sans prendre le droit d’écriture. |
| `submit-text` | Bloc de texte et soumission atomique à une application reconnue ; une ligne ou plusieurs selon la capacité du profil. C’est le chemin commun du wake et de drive. |
| `write` / `paste` / `key` | Primitives supervisées pour les besoins non couverts par `submit-text` ; autorisation ciblée et reçu. Un Enter isolé ne doit jamais soumettre un brouillon humain ou une autre transaction. |
| `resume-application` | Reprise structurée d’une application terminée dans un PTY conservé, avec UUID et preuve de nouvelle incarnation. |
| `interrupt` / `stop` | Actions distinctes, avec droits distincts et cible exacte. Interrompre le CLI ne doit pas tuer le host ni toutes ses sessions. |
| `request-status` / `cancel` | Consultation ou annulation d’une demande encore en attente ; une demande appliquée ne peut pas être « annulée » rétroactivement. |

Le propriétaire humain et le processus propriétaire des PTY sont deux autorités différentes. Le premier délègue les droits ; le second arbitre techniquement leurs effets. L’autorité d’une supervision peut être héritée du mandat de lancement du job, bornée au parent/conducteur, à cette cible, à ces opérations et à sa durée. Un agent tiers ne l’acquiert pas en connaissant le slug, le socket ou un nom de contrôleur.

Pour fonctionner avec une fenêtre attachée sans écrire par-dessus un humain, la proposition est un arbitrage coopératif côté owner, séparé du flux d’observation. Pour un PTY délégué, une fenêtre de supervision peut rester attachée en observation pendant que l’automatisation injecte. Quand l’humain prend la main, il détient la composition jusqu’à sa libération ; les demandes automatiques attendent. Pour un terminal permettant les deux usages, le client attaché doit participer au protocole de remise de la main : l’owner doit connaître les octets en vol et le brouillon, pas seulement le temps depuis la dernière touche.

L’absence de frappe depuis quatre secondes ne prouve jamais qu’une ligne partiellement saisie est vide. Sans adaptateur capable d’attester le point d’insertion, utiliser un mode observation explicite ou un transfert explicite du contrôle tout en gardant la fenêtre ouverte. Un simple contournement de `record.controllerId !== null`, un `--force`, un Ctrl-U ou un takeover qui détache la fenêtre ne satisfait pas la demande. Les nouveaux octets humains qui arrivent avant le commit préemptent la demande ; ceux qui arrivent pendant une transaction déjà engagée restent ordonnés et préservés, sans s’intercaler dans le bloc automatisé. Les limites, délais et annulations doivent être explicites.

> Authorized PTY automation MUST share one owner-side serialized input broker with human input. Attachment alone MUST NOT permanently block automation; active human control, an unfinished human draft, or an unknown safe insertion point MUST defer it. No automation request may clear, submit, overwrite or interleave with a human draft. The attached view MUST remain usable and connected throughout an accepted automation transaction.
>
> Every mutating request MUST carry an authenticated actor, a verifiable delegation or owner grant, an exact target incarnation, an operation, an expiry and an idempotency key. The owner-side application boundary MUST enforce that authorization, the current human-input epoch and the application state. A stale, revoked, unsupported or ambiguous request MUST write zero bytes. Repeated delivery of one committed request MUST NOT submit it twice.
>
> Admission and outcome MUST be auditable using the same request identifier. The receipt MUST distinguish queued, deferred, applied, rejected, expired and delivery-uncertain, and identify the observed target, authority and refusal reason. Payload contents need not be duplicated in audit logs; retain a protected reference or digest and byte count. If durable admission cannot be recorded, the operation MUST fail before mutation. An uncertain post-write outcome MUST remain uncertain until reconciled, never silently retried under a new identity.
>
> Message deposit, wake submission, application receipt and message processing are separate acknowledgements. A successful send MUST NOT imply that the target application has processed the message. Wake state MUST survive a sidecar restart, coalesce pending envelope notifications and retry a deferred request without losing the envelope or duplicating an accepted submission. A deferred native target MUST NOT trigger a fallback into another terminal or a new headless agent.

Cette dernière règle est nécessaire aussi pour la sélection des drivers : le wake `auto` actuel exclut bien le driver headless (`H/src/cli.ts:2157–2158`), mais le `drive auto` général essaie encore native, tmux puis headless (`:3763–3774`). Les résultats doivent distinguer « transport non applicable » et « cible connue mais différée » ; un booléen est insuffisant pour une chaîne sûre. L’adaptateur cluster-mesh `H/src/runtime/drive/pty-actuator.ts` doit conserver ces distinctions et un reçu vérifiable, au lieu de seulement transformer le booléen en `acted/failed`.

La protection contre les réponses du terminal doit couvrir les deux directions et le replay, sans retirer toutes les séquences ANSI. Le texte d’affichage et la restauration des modes restent utiles ; une requête de capacités est une action avec effet, pas un dessin historique à rejouer. Les réponses vivantes nécessaires au TUI doivent continuer à fonctionner. Les parsers doivent être incrémentaux : une réponse ou un marqueur peut traverser plusieurs chunks, une coupure de connexion ou la frontière CLI/shell.

> Historical replay MUST NOT reissue terminal queries. Terminal replies MUST be correlated with live queries and the requesting application incarnation. Replies belonging to a completed application, including split and delayed replies, MUST NOT enter the persistent shell prompt. The host and attached client MUST have one documented responder for each supported query family. Live application queries, human text, bracketed paste, Unicode and normal key sequences MUST retain their semantics.

Pour upgrade et restore, la vue humaine par défaut doit être localisée, concise et structurée autour de ce qui a réellement changé. Le JSON reste accessible explicitement par une option machine, avec objets structurés plutôt que chaînes de JSON encastrées. Exemples de formulation française, uniquement illustratifs : « Paquet installé : X. Frontend actif : X. Moteur PTY encore chargé : Y ; transition différée, 6 sessions conservées. » et « 3 CLI repris, 4 déjà actifs, 2 terminaux rattachés, 5 délégations exclues, 1 reprise différée : saisie humaine en cours. » Aucun compteur ne doit être déduit du nombre de tabs planifiés. Un registre npm indisponible doit se lire « vérification impossible », pas « déjà à jour ».

**E. Upgrade ordonné : ce que #375 apporte, ce qu’elle ne promet pas.** Sur main, `R/src/native-terminal/process.ts` construit host et serveur ensemble. Son arrêt appelle `stopAll`, puis éventuellement `forceStopAll("SIGKILL")` (`:190–205`) ; SIGINT/SIGTERM/SIGHUP sont reliés à ce chemin (`:234–236`). Le guardian de `R/src/pty.ts` contient également les groupes lors de la mort du host. Une commande ajoutée à upgrade qui ferait simplement `host-stop` puis restart ferait perdre les CLI. Le maintien du host chargé n’est donc pas à remplacer par un kill automatique.

`H/src/runtime/upgrade/index.ts:1532–1571` vérifie la version installée, supprime l’installation précédente et conclut « applies on next launch ». Aucune orchestration du processus natif n’est menée. `convergeAfterExplicitUpgrade` équipe les intégrations Claude/Codex/etc. via doctor ; son mot « hosts » ne désigne pas une convergence du processus PTY. Cela explique que le processus du 16/10 puisse exécuter son ancien code après l’installation du 18/10. Une version imprimée par le binaire sur disque ne mesure pas celle de ce processus.

Le code de #375 introduit `owner-process.ts`, `frontend-process.ts` et `owner-protocol.ts`. `PR R/src/native-terminal/owner-process.ts:221–262` expose les composants et, pour `replace-frontend`, démarre/vérifie le candidat ou le rollback retenu, sélectionne le nouveau frontend, puis retire les précédents. L’owner et les CLI restent en vie. `PR H/src/runtime/upgrade/index.ts:1741–1753,1805–1863` prépare la rétention avant le remplacement du paquet, remplace le frontend après vérification et distingue les versions installées, chargées, remplacées ou différées. Le chemin « paquet déjà courant » tente aussi la convergence PTY. Les identités d’écriture/ACK et la reprise du bail ferment la fenêtre d’incertitude lors d’un changement de frontend pour les participants compatibles.

Ces apports sont **implémentés sur la branche**, pas déclarés qualifiés par cette analyse. `PR BRANCH.md:36–61,111–115` dit explicitement que B5 Linux/macOS reste non qualifié sans cohorte réelle non vide, que la cohorte réelle n’est pas tentée sur instruction du propriétaire, et qu’aucun lot L n’est fait. Les verts ciblés consignés dans ce fichier ne remplacent pas cette qualification. Je n’ai pas interrogé la CI distante ni exécuté de campagne.

Il faut lire la spec v3 avec son amendement ultérieur, pas appliquer seulement son texte initial de drainage. `PR BRANCH.md:43–56` conserve l’amendement ratifié : les owners pré-B chargés sans barrière effective restent `admission: unfenced`, `retirement: deferred`. L’upgrade ne leur envoie pas de signal, ne retire pas leur endpoint et ne migre pas leurs sessions ; leurs installations nécessaires restent conservées. Cette coexistence peut durer indéfiniment. Un marqueur ne rend pas un vieux processus coopératif. Cette règle s’applique directement au risque décrit dans le brief.

La phase B rend donc les changements de frontend futurs ordonnés ; elle ne recharge pas un correctif de `host.ts` dans l’owner existant. La phase L doit transférer les masters PTY et leurs états entre owners compatibles avant le retrait de l’ancien. Les sessions pré-guardian-v2 ne deviennent pas transférables par installation du nouveau paquet. La spec v3 exclut leur migration à chaud et distingue aussi le crash d’un owner d’un arrêt planifié. Pour les vieux hosts, la sortie correcte reste une transition différée explicite ou une reprise planifiée des applications selon une décision séparée ; aucune continuité des mêmes processus ne peut être promise.

> Upgrade MUST distinguish installed code from each resident component's loaded code and capabilities. It MUST qualify a candidate and retain a usable rollback before switching. A compatible frontend may be replaced while its PTY owner stays alive; an owner may retire only after its sessions have ended or after a qualified transfer has completed. Existing unfenced pre-B owners MUST retain their sessions and endpoints and MUST be reported as unfenced/deferred. Installing a package MUST NOT be reported as completing an owner restart.

3. Faire refuser avant effet les écritures hors racine dans les tests, y compris fs synchrones, promesses, streams, rotations, rename, chmod et descendants. Couvrir les chemins effectifs et les symlinks, pas seulement une comparaison de chaînes. Les programmes non Node et binaires natifs justifient en complément une sandbox de test qui rend l’état humain inaccessible/inaltérable ; un monkey-patch Node seul ne peut garantir « jamais ».
4. Tester ce refus sur un **faux répertoire propriétaire protégé dans la fixture**, jamais sur le vrai état de l’utilisateur. Déclencher les fins `sess-livelock`, `h2a-alpha`, exception et reconnect ; vérifier que les journaux privés existent et que la fixture protégée n’a aucun changement. Le test doit échouer même si le produit avale l’erreur de journalisation.
5. Propager le confinement aux runners ordinaires, exécutions ciblées et jobs CI. Une convention réservée à un script spécial est insuffisante. Le nettoyage ne vise que les descendants et fichiers créés par la fixture, avec identité/PID de naissance ; aucun kill par nom ni retrait d’un socket découvert dans l’environnement humain.

Le journal réel ne doit pas être nettoyé dans le lot de tests. Le conducteur peut conserver les lignes contaminées comme preuve et les distinguer dans son diagnostic ; leur présence ne justifie ni une purge automatique ni une lecture supplémentaire de l’état réel dans cette mission.
