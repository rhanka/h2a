## 0. How to read this specification

### 0.1 Source tags (mandatory on every decision)

Every decision `D<n>` carries one primary source tag; where a second source independently supports the same statement it is appended after the primary tag, and a part that is only a proposition is tagged separately inside the decision:

| Tag | Meaning |
| --- | --- |
| `owner-verbatim` | Wording supplied as an owner quotation in the commissioning brief or recorded verbatim in `DECISIONS-owner.md`. The date and locus are cited. |
| `both-analyses` | SOL and ASTRA, written independently without seeing each other, converge on the statement. Convergence of two analyses is **not** owner ratification. |
| `proposition-not-validated` | A reconciliation choice, a single-analysis proposal, or a technical proposal that still requires ratification by the competent owner (product owner for principles, repo owner for naming/layout). It must never be implemented or reported as an owner requirement. |

Where a decision mixes a pre-existing ratified capital item with a new proposal, the two parts are separated so that the proposal cannot inherit the capital item's authority.

### 0.2 Normative language

`SHALL` / `MUST NOT` below state the proposed contract. They acquire force only at ratification of the corresponding decision. Decisions tagged `proposition-not-validated` keep `SHALL` wording so that a RED test can be written against them, but their tag governs.

## 1. Goal, scope, non-goals

### 1.1 Goal

Deliver the full round trip, not only an editable field: `focus build` → in-place Tiptap editing inside the rendered dossier → one structured return (answers + notes + per-paragraph edit diff) → the producing agent (or a designated successor) → application to the source, conflicts surfaced, receipt issued.

The first increment works offline, in a standalone HTML host, without waiting for a document server, a CRDT, a future MCP Apps component, or the diagram-engine deliveries blocked in PR #377.

### 1.2 In scope (first increment)

- A framework-neutral edit contract owned by Focus: paragraph identities, an editing manifest, a per-paragraph `before`/`after` diff, and a pure reconciler.
- A reusable Tiptap editor surface (ownership: see D10, proposition).
- Extension of the existing `focus build` portable kit as the first qualified offline host.
- A tested consumer path so the producing agent can import, reconcile, apply, and issue a receipt.
- User-language UI with embedded catalogues; source content language untouched.

### 1.3 Out of scope (see §9 for the exhaustive NOT-covered list)

Connected multi-writer application to shared sources is a later lot with real compare-and-swap control. Full table/diagram/code-block editing, collaborative editing, and automatic Track writes from a `file://` page are not part of the first increment and must not be announced as delivered with it.

### D11 — The dossier snapshot stays immutable; edit capability lives in the host envelope — `both-analyses`

The snapshot document, its closed schemas and its `enabled: false` affordances are not modified to enable editing (K3). A qualified host declares a distinct local-draft edit capability in its own envelope. Five notions sharing the "amend" root stay separate and are never merged into one enum (ASTRA B4): the `amend` affordance *name* in the document, the `amendment` value of `OutcomeModality`, the Track binding action `amendSpec`, the WorkEvent kind `item.spec-amend`, and the persisted event `spec.amended`. An edit draft is a proposed textual amendment; it selects no option, ratifies no outcome, attests no comprehension, and a `section:*` `targetRef` never yields a Track `itemId` by convention.

### D12 — Editing is source-faithful and happens before presentation — `both-analyses`

The editor loads source fields, before `preparePresentation` and before any renderer decoration (K4). Opening, focusing, rendering, switching theme or UI locale, or leaving an unchanged editor produces no change. Unchanged source content is preserved verbatim, byte for byte at the value level. The editor is mounted in place of the rendered text in a dedicated dossier-level amend mode; it is never nested inside the whole-card option `<button>` elements of the current kit, so typing in text can never trigger the enclosing option's selection (SOL B). Read rendering keeps DS defaults (selectable cards, no proliferation of per-option actions); that layout concern belongs to the component/renderer, never to a layout hint written by an agent into the dossier.

### D13 — Persistent opaque paragraph identity, carried by a versioned manifest sidecar — `both-analyses`

Each editable text unit is addressed by the five-tuple `(documentRef, nodeId, targetRef, field, paragraphId)` (V5). `nodeId` selects the node and `targetRef` must match that same node; duplicate or inconsistent addresses refuse reconciliation. `paragraphId` values are opaque, unique within the document lineage, persisted by the producer in a versioned editing manifest kept *with* the source, embedded by the host in the portable artefact, and returned with any newly allocated identities. Initial identities for a legacy document are seeded once, deterministically on the same base, before first editable publication; their seed position is not their permanent identity. Surviving identities are carried forward across rebuilds and agent revisions; deleted identities are never reassigned. Display order, array indexes, DOM paths, translated labels, content hashes and character offsets are never identities; a source range or ordinal inside the manifest is baseline-local mapping metadata only, with its unit declared. Translating document *content* is a content revision: correspondence must be carried explicitly or reported unresolved, and a stable ID never authorises applying an edit whose precondition no longer matches. Manifest and return have their own schema versions; dossier schema v1 bytes/URN and PR #377's evidence v2 are untouched (K3, K7). Embedding the manifest into the canonical document model later would be an explicit schema evolution with a migration (NOT covered, §9).

### D14 — Per-paragraph change semantics — `both-analyses` (paste-identity detail: `proposition-not-validated`, V4)

Each change carries exact `before` and `after` content in its declared format (`text/plain` for plain fields, which stay plain; a declared round-trip-tested Markdown profile for Markdown fields). Constraints: `replace` requires both values present; `insert` requires `before: null` and a present `after`; `delete` requires a present `before` and `after: null`; `move` preserves content and changes structural anchors only. `null` means absent; `""` is content. Split and merge are grouped paragraph changes inside one atomic transaction, never an undocumented whole-string rewrite: split keeps the original identity on the leading (SOL) / one declared surviving (ASTRA) paragraph — this specification adopts *leading* as the deterministic default survivor, proposition — and allocates new identities to the following paragraphs; merge keeps the leading identity and deletes the consumed ones. Structural anchors name `parentId`, `previousParagraphId`, `nextParagraphId` with explicit `null` at boundaries, never a renderer index alone. Repeated typing is coalesced against the declared baseline; an unchanged paragraph is never emitted *as a change*; undoing everything yields an empty cumulative delta (zero paragraph changes). An empty delta is not the same as "no return": when it supersedes a previously frozen return against the same baseline, it is still exported as a frozen superseding return carrying the lineage forward, so that the revocation can be consumed and the superseded return can never be applied late (D16–D18, §5.4; lineage detail `proposition-not-validated` with D21). Paste allocates fresh identities and pasted markup never supplies trusted identities (proposition, V4); undo may restore the identity of the same removed logical paragraph. Pasted links, scripts, remote images and raw HTML stay inert or are rejected according to the declared profile — introducing rich rendering re-opens a surface the current plain-text kit display avoided, and FE-2/FE-3 test it as such.

### D15 — Three digest domains stay distinct; the inherited `hash` is preserved — `both-analyses` (canonicalisation profile: convergent proposition)

(1) The dossier's opaque `hash` and `cursor` are carried verbatim and keep their existing meaning (K5). (2) A new document `baseHash` is a recomputable digest of the exact canonical authoring snapshot that was edited, computed before ecosystem/diagram expansion and before `preparePresentation`, over canonical JSON *values* (not file indentation). Both analyses propose RFC 8785 canonicalisation, UTF-8 encoding, SHA-256, `sha256:` prefix; this profile is adopted as the v1 contract proposal, subject to FE-0 cross-review. No trimming, no Unicode normalisation, no translation of source strings before digesting. `baseHash` is not stored inside the hashed dossier document, so it has no self-reference. (3) The manifest bound to that same baseline carries its own hash, `manifestBaseHash`: identical source text with different paragraph identities is a different editing base. Its hashed domain is fixed exactly as follows (v2 correction; v1 left it implicit, which made the computation self-referential or implementation-defined): `manifestBaseHash` is the digest, under the same canonicalisation profile, of the canonical manifest projection obtained by **removing the `manifestBaseHash` field itself** (absent — not `null`, not `""`) and hashing every remaining field as a JSON value: `schemaVersion`, `manifestId`, `documentRef`, `baseHash`, `fields[]` and `paragraphs[]`, with arrays hashed in their stored order (canonicalisation orders object keys, never array elements; sibling order is therefore part of the hashed mapping). In v1 of the manifest contract, `manifestBaseHash` is the *only* excluded field: any future field is hashed by default unless a later schema version explicitly redefines the projection, and host transient metadata (capture time, file paths, session hints) must live outside the manifest, never inside the hashed projection. FE-0 publishes shared reference vectors (manifest fixture -> expected `manifestBaseHash`) that the build, the browser host and the importer must all reproduce bit for bit before the vocabulary is frozen. The frozen return additionally carries a canonical content digest that excludes its own field (V6), by the same absent-not-null rule. PR #377 envelope/renderer/validator digests remain build-artefact integrity only (K7). No digest computed in the browser is ever presented as a Track specification `resultHash` (D19). The build computes these digests once per build and binds the exposed editable fields to that base; they are never recomputed per keystroke (C13), and no duplication of a large evidence corpus is needed to compute them.

### D16 — One pure reconciler; atomic publication; CAS for connected application — `both-analyses` (return-lineage register and revocation computation: `proposition-not-validated` with D21)

Reconciliation is a pure operation over (retained baseline document + manifest, current authoritative document + manifest, edit return, return-lineage state for that baseline) producing either a candidate (new source + updated manifest + updated lineage state) or structured conflicts. Lineage state is data passed in and out; persisting it durably is the host's duty (FE-5), never an I/O performed by the reconciler.

Cumulative lineage semantics (v2 completion of V3/D21, completed in v3 for transitive supersession; v1 named cumulative supersession without defining revocation or late delivery, which both v1 reviews flagged as P1, and v2 still transported only the immediate predecessor, which both v2 confirmation reviews flagged as the remaining P1). Each return in a lineage states the **complete desired delta against its named baseline**, never an incremental patch on top of its predecessor's result. Each frozen return also transports its **complete ancestry**: alongside `supersedesReturnId` (immediate predecessor, absent for the first return of a lineage), `supersededReturnIds[]` lists *every* return it transitively supersedes against that same baseline, immediate predecessor first, then each older ancestor in chain order (construction: `[supersedesReturnId, ...predecessor.supersededReturnIds]`; `[]` for the first return; no duplicates; never its own `returnId`; covered by the frozen return digest like any other return content). Ancestry is therefore provable from a single delivered return, with no need to receive the intermediates. The lineage state for a baseline records: the current head `returnId` with its `supersededReturnIds[]`; every seen `returnId` with its content digest; a superseded tombstone for every `returnId` listed in an *accepted* head's `supersededReturnIds[]` — tombstones form a monotone set that only an accepted head extends, including predecessors never directly received and including when the superseding return carries zero transactions; and, for every application, a per-transaction application record (consumed `returnId`/transaction/change IDs, the actual base and result digests, and for each applied change its address, `before`, `after` and structural anchors as applied). Processing a new head then works as specified in §5.4: a return that is already superseded by the registered head (directly or through a tombstone) is refused as superseded and is never applied, even if every `before` precondition still matches the current source; two distinct successors claiming the same predecessor with no order between them form a fork and yield a conflict with no silent winner (`proposition-not-validated` detail), as does any return whose order relative to the registered head the transported ancestry does not prove — such a return is refused as lineage-order-indeterminate and is never applied, and arrival order, capture timestamps and content equality never prove lineage order; for a valid new head (one proven to succeed the registered head, §5.4 step 3), the reconciler computes the *remaining* transition from the current source to the desired state (baseline + head delta). Current content is treated as attributable to this lineage only where it matches the application records *and* still equals the recorded applied result for the affected units and topology — matching `after` text alone never proves attribution. Attributable content that the new head no longer requests is revoked as part of that same atomic remaining transition (full revocation A->B->A and partial, per-paragraph revocation included); content changed by a third party after the lineage application is never overwritten by a revocation and yields a conflict carrying baseline / lineage-applied (when it exists) / current / requested values. Even when `baseHash` matches, every affected `before` value and structural precondition must still match. Matching `after` content alone never proves a transaction was already applied; receipts provide idempotency (D17). A conflicting member blocks the whole submitted batch; a later explicit split creates newly identified batches and is never a hidden partial success. A rebased candidate names its actual application base and its real base/result digests describe the current-to-result transition actually performed; the original return remains available as provenance. Offline, the re-read happens at import by the producer. Connected, the host performs the final version check and the publication inside one compare-and-swap or equivalent single-writer boundary (FE-6); the rendered dossier never oscillates between paragraphs of different versions. On conflict the user's draft is preserved, never erased. Original comprehension attestations remain evidence about the original text; they never become attestations of amended content, and a re-rendered amended dossier is re-validated (structure, readability) before presentation, while a temporarily incomplete *draft* remains exportable as a correction return.

### D17 — One frozen return envelope; JSON is the reference, YAML is equivalent; idempotency by identity and digest — `both-analyses`

Answers, notes and `editReturn` are serialised from one immutable return value whose version makes edit support explicit. Existing answer shapes are adapted through a versioned adapter, never silently reshaped (K10); a text correction is never turned into a question answer, nor free text into a dossier replacement. JSON is the reference data representation. YAML, when offered, decodes to the same typed value under a restricted JSON-compatible data model: duplicate keys and custom tags are rejected (ASTRA). An export captures one completed editor revision — no lost last keystroke, no active IME composition, no pending diff, no concurrently updated answer omitted — and freezes it: copying, downloading, sending and retrying that frozen return preserve its `returnId` and digest. Reusing an ID with different content fails; consumers keep a processed-return and lineage record (D16) and verify content equality, in addition to any transport token (K11). Re-exporting the *same* frozen return creates no new identity; exporting after the desired delta against the baseline has changed — including after undoing back to an empty delta — creates a new frozen return with a new `returnId`, `supersedesReturnId` naming the previous head and `supersededReturnIds[]` carrying the complete transitive ancestry (`[previous head, ...previous head's supersededReturnIds]`, D16), even when its `transactions[]` is empty. The exporter builds that list only from the previous frozen return (or the session/recovery record of it, §5.5); ancestry it cannot recover is never guessed, and no superseding return is frozen on a truncated list presented as complete — recovering/importing the previous frozen return is what restores the ancestry (§5.5). Consumer-side, a return whose transported ancestry is missing or internally inconsistent fails validation (§5.4 step 1), and an internally valid return whose order against the registered head its ancestry does not prove (for example a non-conforming list truncated to the immediate predecessor) is refused as lineage-order-indeterminate (§5.4 step 3 (3e)). A host must never suppress that empty superseding return as "nothing to export" when a prior frozen return exists for the same baseline in the session, because the empty return is precisely what carries the revocation and the tombstones (§5.4, §5.5). Capture timestamps and similar host metadata are produced by the host, never by the pure core. Protocol primitives and enums stay in English; `before`/`after` and note values stay in the document's real language.

### D18 — The producing agent is the consumer of record; states and receipts are explicit — `both-analyses`

Before presenting a dossier as editable, the producer retains the baseline document, its manifest and a production generation reference; the host envelope carries opaque producer/generation correlation (a file path or a session name alone is not a durable identity), and the free-text `provenance.source` is never treated as a file-open instruction (SOL C). The consumer sequence is normative: (1) parse and validate version, identities, digest and correlation; (2) load the retained baseline, re-read the current source, and check the processed-return and lineage record *before* evaluating paragraph preconditions — a return already superseded by the registered head (its `returnId` appears in the head's transported `supersededReturnIds[]` or in the tombstone set) is refused as superseded at this step, a return whose order relative to the registered head its transported ancestry does not prove is refused as lineage-order-indeterminate at this step, and preconditions can never resurrect either (D16, §5.4); (3) resolve every paragraph and prepare the whole remaining transition — user corrections are applied with their exact words, revocations restore the baseline wording only where the current content is attributable to this lineage's recorded application, any further agent adaptation is a separate, agent-attributed change, and an inapplicable correction or revocation is reported with its cause and its original text kept; (4) publish the new source, the coherent updated manifest and the updated lineage/application records through the host mechanism, rebuild the presentation, and leave out-of-scope sources/citations untouched; (5) only then, if an instructed specification amendment applies, build the Track record (D19); (6) issue a per-transaction receipt: applied / revocation applied / already processed / superseded (not applied) / lineage-order-indeterminate (not applied) / conflict / unsupported or not applicable with reason, naming the exact `returnId`/transaction/change IDs consumed or refused, the actual base/result digests when applied, and the resulting artefact or Track event references when they exist. A receipt is also issued for an empty superseding return (revocation applied, or already at the desired state), for a refused late superseded delivery and for an indeterminate-order refusal, so the sender can distinguish "revoked", "never applied", "order not provable" and "still in flight". The Focus skill documents this consumption; the snapshot registry entry gains no write permission by a prose edit — capabilities and parameter versions are explicit registry data (K14, FE-5).

### D19 — Track records instructed amendments only; no new event kind in the first round trip — `both-analyses`

The chain is: paragraph-diff return -> reconciliation and application by a qualified host -> conditional translation to Track. Only a specification amendment that was actually instructed, authorised through the Track write path, applied to an identified item's real source, becomes an `item.spec-amend` WorkEvent with that source's true `baseHash`, an RFC 6902 `patch` (typically `test`+`replace` operations on paths resolved from identities *after* re-reading the current base — JSON Pointer array indexes computed at that moment never become return identities) and its true `resultHash`. Several paragraph corrections may rebuild one Markdown field and yield a single field `replace`; the editorial before/after remains available in the return artefact, which no summary replaces. A local draft, a mere export, a prose correction, a dossier-only revision, and a standalone dossier without a Track item/decision produce **no** `spec.amended` event, and no `itemId` is ever invented from `ref` or `targetRef`. The complete return and its receipt live as host artefacts; a genuine rendered comparison view may be attached through the existing `rendered-view` mechanism, but a feedback JSON is never disguised as one (K12). A durable host-side index may already associate return, receipt and event. Source publication and Track append are not one existing transaction: the host keeps a durable receipt and idempotent recovery across the crash windows of V15, respecting Track's append-only single-writer rule, and the UI keeps "source applied" and "recorded in Track" distinct until recovery joins them.

### D20 — A declared editable profile; everything else is preserved and visibly non-editable — `both-analyses` (list-paragraph inclusion gated by evidence, V7)

"Practical paragraph" is defined by a declared semantic segmentation of the source field under the stated content profile — never by splitting on blank lines and never by selecting rendered `<p>` elements, both of which nested lists, table cells, headings and code blocks invalidate. Profile P0 (first increment) covers: prose paragraphs of `prose` nodes; explicitly allow-listed narrative text fields of questions/options; headings only as typed blocks if the profile declares them. List-item paragraphs (present in the reference `s-reco`) enter P0 only when FE-1/FE-2 round-trip tests prove them; until then they are preserved non-editable. A table cell requires table/cell identity in addition to any paragraph identity; code blocks and diagrams are opaque blocks until a dedicated editor profile exists. Presentation labels, source hashes, signed evidence, original citations, evidence bytes, historical trace entries and application state never become editable merely because they are visible. The editor must make it impossible to run a transform that would destroy an unsupported block: unsupported content is carried through unchanged or reported as explicitly affected content inside the transaction, never changed outside the reported transaction. The first delivery is announced exactly as "P0 fields editable, other blocks preserved" — never as "the whole document is editable".

### D21 — Canonical names and cumulative replay semantics — `proposition-not-validated`

To make RED tests writable before ratification, this specification adopts one concrete vocabulary (V1–V3, V11): package directory `packages/focus/src/editing/`; schemas `packages/focus/schemas/focus-edit-return.v1.schema.json` and `focus-editing-manifest.v1.schema.json`; sidecar type name `FocusEditingManifest`; return envelope discriminator and field names as in §5; `editReturn.transactions[]`; `mode: "cumulative"` with `supersedesReturnId` (immediate predecessor) and `supersededReturnIds[]` (complete transitive ancestry, immediate predecessor first) when a new frozen return replaces a previous one against the same baseline, with the v2 lineage completion of D16 as completed in v3 (complete-desired-delta semantics, transported complete ancestry, durable head/tombstone/application records, empty superseding returns, fork and unproven order as fail-closed refusals); h2a-side consumer files under the `focus-feedback` stem. SOL's alternative vocabulary (`src/edit/`, `FocusReturn`, "editable projection", single changeset, `focus-return` files) is recorded in §3.2 and remains a legitimate renaming candidate **before** FE-0 merges; after FE-0 merges, renaming requires a schema-versioned migration, so the FE-0 cross-review (Focus + DS) must explicitly confirm or replace this vocabulary. No consumer may implement against both vocabularies.

### D22 — Performance is qualified by measurement, then by budgets fixed and verified before acceptance — `proposition-not-validated`

Following SOL against fixing numbers in advance (V9), in two phases inside FE-8 (v2 correction; v1 stopped after phase A, which would have let an arbitrarily slow editor pass every gate). **Phase A — measure:** FE-8 measures keystroke->paint, edit-mode activation, ordinary-paragraph local validation, large paste, export, open and resume on the frozen representative corpus (reusing the large PR #377 corpus where available) across declared browser/hardware profiles, and publishes the profiles, corpus and sampling protocol with the results. **Phase B — fix and verify budgets, before acceptance:** from the phase-A measurements, FE-8 writes explicit budgets into the performance policy file — per metric: statistic (for example p95), budget value, corpus, profile and sample protocol — and a verification run must pass those budgets on the declared profiles. Phase B is part of the FE-8 gate and of first-increment acceptance (§6.1); publishing measurements alone never qualifies reactivity. ASTRA's candidate budgets (p95 keystroke->paint <= 50 ms; ordinary-paragraph local validation <= 100 ms) are recorded as candidates to confirm or revise from phase-A measurements; they are neither imposed in advance nor droppable without trace: any revised budget carries its measurement-based rationale in the lot report, and a budget that cannot be met is a failed gate to escalate, never a silently waived one. Behavioural invariants that need no numbers are gates immediately: no canvas or evidence-reader remount on a keystroke, no whole-dossier re-parse or whole-envelope re-hash on a keystroke, caret/selection/scroll preserved across locale/theme changes and evidence reading, stale asynchronous results never overwrite newer local input, and the exported return equals exactly the displayed revision.

### D23 — At most one temporary editor fallback inside focus-kit, with a replacement gate — `proposition-not-validated`

If, and only if, the DS component of D10 cannot be delivered or consumed in time for the first witness, lot FE-3 may carry one thin, minimal Tiptap adapter inside `focus-kit`, built against the same Focus contract and passing the same FE-2 RED test list applied to the adapter surface. Conditions: the lot records the fallback as temporary with a named replacement gate (swap to the published DS export, then delete the adapter); the sentropic `EditableInput` business wrapper (autosave, `apiPut`, app stores) is never copied; the step is never reported as a completed DS extraction; maintaining two editors beyond the replacement gate is a defect, not an option. This fallback needs explicit go-ahead from the FE-3 lot owner at lot start; the default path remains the DS component.

### D24 — Separation from PR #377 and from future hosts — `both-analyses`

Editing is delivered on its own narrow branches, rebased/coordinated over the shared surfaces PR #377 also touches (`model.ts`, validation, `App.svelte`, `focus-build.ts`, renderer manifest, generated assets), without converting the evidence PR into a general editor delivery and without inventing a third kit variant. Tiptap prose editing has no functional dependency on diagram layout/render engines; it must preserve PR #377 evidence reading and canvas state. Generated artefacts (`renderer.html`, `renderer-manifest.json`, `validator.mjs`, vendored Focus copies under `packages/track/src/focus-vendor/`, generated registry entries, schema copies) are regenerated exclusively through their existing scripts (`scripts/build-focus-dossier.mjs`, `scripts/vendor-focus.mjs`, `scripts/check-focus-vendor.mjs` and the renderer build path), never hand-maintained. Future hosts (MCP `ui://` per owner H-4, a `renderHtml`+runtime host per V13, the `focus-interactive` deck) consume the same contract through adapters; none of them redefines the return, and none is an acceptance gate for the first increment.

### 5.4 Reconciliation algorithm (contract level)

1. Validate envelope/manifest versions, address consistency (D13), operation invariants (D14), digests — including recomputation of `manifestBaseHash` over the D15 projection — production correlation, and internal ancestry consistency: `supersededReturnIds[]` present, duplicate-free and free of the return's own `returnId`; empty if and only if `supersedesReturnId` is absent; otherwise its first element equals `supersedesReturnId` (cross-field equalities are semantic-layer checks, FE-0 (M); a failure here is a validation refusal, never a reason to reconstruct ancestry by guessing).
2. Load the retained baseline (document + manifest) identified by `baseHash`/`manifestBaseHash`, the lineage state for that baseline (D16), and re-read the current authoritative document + manifest.
3. **Lineage check, before any paragraph precondition, fail-closed.** Let `H` be the registered head for this baseline (if any), with its recorded `supersededReturnIds(H)`, and `T` the tombstone set (the union of the `supersededReturnIds[]` of every accepted head; only an accepted head extends it). Lineage order is proven *only* by the transported ancestry — the candidate's `supersededReturnIds[]` compared with the registered lists, within the same baseline lineage — never by arrival order, capture timestamps, content equality or paragraph preconditions; identifiers known only under another baseline prove nothing here. The branches apply in this order: (3a) same `returnId` + same digest -> already processed (receipt replay, no second application); (3b) same `returnId` + different digest -> refusal; (3c) **positively superseded** — the candidate's `returnId` is in `T` or in `supersededReturnIds(H)` -> refusal as superseded, with a receipt; its `before`/structural preconditions are never evaluated as a path to application, so a late delivery cannot resurrect a revoked correction (this is what refuses a late R1 after an R3 carrying `supersededReturnIds: [R2, R1]` was processed first, R2 never having been delivered); (3d) **proven successor** — either no head is registered yet, or `H`'s `returnId` occurs in the candidate's `supersededReturnIds[]` *and* the subsequence after `H` equals `supersededReturnIds(H)` exactly (sequence equality, immediate-first order), so the candidate's ancestry is a consistent extension of the head's, possibly through intermediates never received -> candidate new head: on acceptance, every identifier in its `supersededReturnIds[]` is tombstoned (added to `T`), including those intermediates and including when its own `transactions[]` is empty; (3e) **otherwise, order indeterminate** — the candidate neither is positively superseded under (3c) nor proves succession under (3d): fork (including two distinct returns claiming the same `supersedesReturnId` predecessor with no order between them), incomparable lineage roots for the same baseline, a subsequence after `H` diverging from `supersededReturnIds(H)`, or an internally valid ancestry that proves no order against `H` (for example truncated to the immediate predecessor) -> refusal as lineage-order-indeterminate (the fork subcase is reported as a fork conflict), with a receipt, zero changes applied, head and `T` unchanged — a refused return never advances the head or the tombstone set — and its preconditions never evaluated as a path to application. Resolution requires a new frozen return whose transported ancestry proves (3d) against the *current* head, or explicit arbitration (Q3, §9 item 17); there is no silent winner, no first-delivered-wins and no timestamp race. In particular, an R1 delivered after its successor R3 with R2 absent is refused under (3c) when R3 transported the full ancestry `[R2, R1]`, and under (3e) when no usable ancestry makes its order provable: in both cases `B` is never re-applied.
4. **Compute the remaining transition.** Derive the desired state (baseline + candidate head delta) and resolve every affected address in the current manifest. For each affected unit and its topology, attribute the current content: (a) still at baseline -> apply the desired change if its `before`/structural preconditions match; (b) equal to this lineage's recorded application (application record match *and* current still equals the recorded applied result) -> keep what the head still requests, generate the inverse for what it no longer requests (revocation, full or partial), apply the difference for what it changed further (A->B then A->C); (c) diverged by a third party, missing target, ambiguous mapping, unsupported format/version, or precondition mismatch -> structured conflict for the batch (baseline / lineage-applied when it exists / current / requested values included), zero changes applied, draft preserved. Content equality with a recorded `after` value, without the application record, counts as case (c), never as attribution.
5. Changes whose targets and topology are untouched by intervening divergence may be rebased onto the current base; the candidate records that actual base. Divergence elsewhere in the dossier does not by itself block the batch. Reconciler-generated revocation inverses belong to the same atomic batch as the rest of the remaining transition; the original returns remain available as provenance and are never rewritten.
6. Publish candidate document + updated manifest + updated lineage/application records atomically under the host boundary as far as that boundary extends (offline: the producer's file operation; connected: CAS/single-writer, FE-6). Rebuild presentation from the new source; never patch rendered output.
7. Emit the receipt (D18), including for refusals at step 3 and for empty-head revocations. Advance the editing baseline only from the acknowledged new version; until then the lineage stays anchored to the same baseline, which is what makes cumulative re-diffing well-defined.

Worked lineage cases (normative outcomes; RED witnesses in FE-1/FE-5): (i) R1 `A->B` applied, then R2 (empty, superseding R1) -> remaining transition `B->A` applied as a revocation if, and only if, `B` is still the recorded applied result; if a third party changed the paragraph after R1, conflict, third-party text preserved. (ii) R2 (empty, superseding R1) delivered *before* R1 -> source stays at `A`, R1 is tombstoned, and the later R1 delivery is refused as superseded although its preconditions still match. (iii) R1 `{p: A->B, q: X->Y}` applied, then R2 `{q: X->Y}` superseding R1 -> `p` is revoked to `A`, `q` is left at `Y` with no double application. (iv) R1 `A->B` applied, then R2 `A->C` superseding R1 -> remaining transition `B->C` under the same attribution rule. (v) **Missing intermediate (three returns, same baseline):** R1 `A->B`; R2 `A->C` superseding R1 (`supersededReturnIds: [R1]`); R3 empty superseding R2 (`supersededReturnIds: [R2, R1]`). Delivery order R3, then R1, R2 never delivered -> R3 is accepted as head (no prior head), the source stays at `A`, R2 and R1 are tombstoned from R3's transported ancestry alone, and the late R1 is refused as positively superseded although its preconditions still match; `B` (and `C`) are never applied. Variant with ancestry proving no order (for example a non-conforming R3 carrying only `[R2]`, accepted as head with R2 alone tombstoned, or R1 in no way ordered against the registered head): the late R1 is refused as lineage-order-indeterminate under step 3 (3e) instead — still never applied, head unchanged, receipt issued. (A return missing `supersededReturnIds[]` altogether never reaches step 3: it fails validation at step 1, with a receipt, and advances nothing.)

### 5.5 Offline behaviour and draft recovery

Reading, editing, undo/redo, diff preview, export and import require no network (D5). The artefact continues to enforce its offline policy (the current kit's `connect-src 'none'` posture is preserved; the portable file never gains an implicit network connection when the connected lot lands). Recovery storage is keyed to (`documentRef`, `baseHash`, `manifestBaseHash`) and also remembers the last frozen `returnId` exported from this browser profile for that key **together with its full `supersededReturnIds[]`**, so that a later export can build the complete transitive ancestry by induction (D16–D17) and so that a draft undone back to the baseline after an export still offers (and can produce) the empty superseding return instead of reporting "nothing to export" (D17): a draft recovered against a different base is offered as an explicit import to reconcile, never silently applied (C16). If that ancestry cannot be recovered (fresh profile, lost storage, only the immediate predecessor known), the exporter never fabricates the missing ancestors and freezes no superseding return on a truncated list presented as complete: importing the previous frozen return restores the ancestry (D17). Any return nevertheless received with an ancestry proving no order against the head is settled consumer-side by the fail-closed rule (§5.4 step 3 (3e)). A complete exportable return (including manifest lineage for newly created paragraphs, its full `supersededReturnIds[]`, and including an empty superseding return) is the cross-machine continuity mechanism of the first increment — importing the previous frozen return on another machine is what supplies its ancestry there; `localStorage` is a supplement whose absence, corruption, fresh profile, or a moved file path must all remain supported by explicit export/import (FE-4 RED). Clipboard denial leaves a complete download and a selectable text representation of the same frozen value.

### 5.6 Authority and security boundaries

The portable file holds no authenticated ingest channel and asserts no identity: nothing in the return payload (including any author-like field) confers Track write authority (K11). Authority exists only at consumption/application time, in the consumer's existing mandate and host context. The resolver treats every string in the return — including `provenance.source`, scope hints and pasted markup — as untrusted data, never as an instruction (no path opening, no identity adoption, no executable content). Rich rendering of edited Markdown passes through the host's existing sanitisation hooks, which must be verified to preserve the anchor attributes the contract needs while keeping hostile content inert (FE-3 RED). Wrong workspace, missing item, unauthenticated channel and stale-base cases refuse at the host boundary in the connected lot (FE-6 RED).

### 5.7 Editor component surface (consumer-side requirement; ownership per D10)

Whoever ships the reusable component, its surface is: controlled document in / transactions out; paragraph-identity attributes carried as editor attributes supplied and interpreted by the Focus adapter, so ProseMirror positions and Tiptap JSON never leak into the wire contract; `editable`/`disabled`/read-only states taking effect immediately (a locked editor cannot type, paste or trigger any save — K8 viewer rule); selection and caret preserved across controlled external updates, with a concurrent external update during typing surfaced rather than silently overwriting local work; IME composition respected (no diff, no export capture mid-composition); undo/redo, Enter-split and Backspace-merge preserving the identity rules of D14; labels, accessibility names and status text injected by the host (no built-in natural language); no network access, no persistence, no business API, no Track or Focus-model types inside the component; unmount leaves no listeners. Mounting is on demand per active field (D6, C13).

### 5.8 Language

Renderers and editor controls receive locale + message catalogue from the host. Injected labels in the pure renderers (`src/render/{hooks,html,md,terminal}.ts`), the kit UI, the HTML `lang` attribute emitted by the builder, copy/export/status notices and accessibility names all resolve through catalogues; the portable artefact embeds the resolved catalogue it needs and fetches none at runtime (D5, D7). Document content language and UI locale are independent axes: rendering the same source + manifest under another locale changes no identity, no diff, no stored value. Registry locale widening beyond `en|fr` is a versioned registry change; the historical entry keeps rejecting values it does not declare (K14).

Catalogue resolution, injection and the missing-catalogue path (D7): (1) *Resolve at production/build time* — the host/producer resolves the requested BCP 47 locale to a message catalogue before or during the build; this is the step at which the producing agent supplies an existing catalogue or produces one from the English reference catalogue, so no agent and no network are needed later by the offline file. (2) *Inject and embed* — the resolved catalogue is passed to the renderers/component as data and embedded in the portable artefact; message keys and paragraph identities stay language-neutral. (3) *Missing locale or missing keys* — every unresolved message renders as an explicit `untranslated` marker (a neutral, key-based, visibly flagged placeholder; its exact visual form is fixed in FE-8 with the DS, `proposition-not-validated`), the HTML `lang` still names the requested locale, and the build report/build manifest lists the locale and the missing keys. The build does not fail solely for a missing catalogue, no message silently falls back to hard-coded French, and a marker is never presented as a translation: delivery notes must name marker-only locales as untranslated, not as supported languages (G6). Silent fallback to hard-coded French remains a defect (D7); a project-local strict policy that blocks builds on `untranslated` keys is allowed only as a separately ratified policy, never as a consequence attributed to D7.

## 6. Lots — RED tests first, exact files per owning repository, gates

Rules applying to every lot:

- **[N]** marks a proposed new file that does not exist at specification time. Unmarked paths are named as existing in the pinned sources by the input analyses (Appendix A); each lot re-inventories its surfaces at lot start (D24, U5) and reports any path that has moved instead of silently substituting another. Paths are relative to the owning repository named in the lot header.
- **RED first.** The lot's RED tests are written and *observed failing for the stated reason* before the implementation lands. A RED test that silently skips because real owner state is absent counts as **FAILED**, not as neutral.
- **Targeted runs only.** Developers run the targeted test files named per lot (`vitest run <file>` for TypeScript `.spec.ts` suites, `node --test <file>` for Node test files, through each repository's own pinned tooling and scripts, to be confirmed from its `package.json`/Makefile at lot start). The full repository suite is run once by the conductor at integration; no lot substitutes a local full-suite run for its targeted gates, and no lot narrows or skips a failing test to turn a run green.
- **Isolation.** Tests use temporary directories only (`mkdtemp`, `XDG_RUNTIME_DIR` pointed at a temporary directory the test creates). No test touches the real h2a state, the real native host, the **owner's installed distribution or user/global `h2a` binary**, or any process the test did not start; processes are stopped only by PIDs the test spawned (never by pattern). One explicit exception, required by the FE-4/G5 distribution gate and allowed nowhere else (v2 correction; v1's unqualified ban contradicted that gate): a test may install the *just-built tarball under test* into a prefix inside its own temporary directory and execute that copy by absolute path, with `HOME` and every `XDG_*` directory (config, state, runtime, cache) redirected inside the same temporary tree, the network blocked, no checkout imports, and the whole tree discarded afterwards. That ephemeral copy is test state, not the owner's installation: resolving `h2a` through `PATH`, reusing a pre-existing prefix, or letting the copy discover real user state voids the gate and counts as an isolation breach.
- **Red-before/green-after proof.** Each regression named in a RED list is reported with the failing command + output before the fix and the passing command + output after. No green is claimed without the command and its output.
- **Generated files** are regenerated via their scripts only (D24) and are listed as delivery steps, never as hand-edited sources.
- **Commits**: conventional English subject, no attribution trailer of any kind; own branch only, fast-forward push, never force; `main` is never touched directly. No Python anywhere (implementation, tests, jobs, one-off scripts).

## 8. Open questions to the owner — kept OPEN, on principles

The following questions merge SOL §E (4 questions) and ASTRA §E (4 questions), which address the same four principles from slightly different angles. They are **not answered by this specification**. Each analysis's recommendation is recorded as a recommendation only. None of them reopens what is already decided: Tiptap, per-paragraph diff return, offline operation, reactivity/atomicity, extending `focus build` now, lossless return, user language. None of them blocks FE-0/FE-1 contract tests; their blocking scope is stated per question. Per the owner's recorded method, a question of this weight is presented with context, options and a recommendation — through a Focus decision dossier with a diagram when a real choice must be made — never as a bare question.

### Q1 — What force should a correction made directly in the dossier carry?

Context (both analyses): the same surface can reword the dossier, correct an answer, or request a change to an upstream specification. Today, editing, option selection and Track amendment are distinct acts, and the standalone HTML has no authenticated ingest channel. A corrected wording can be an exact text to adopt, a reorientation, or an observation; none of these nuances can be inferred from an "accept" button or from the text change alone.

Open question: in your way of working, at which moment should a text correction become an instruction to the producer, then a recorded amendment — and which acts do you want always kept explicitly distinct? What restitution lets you verify the correction was understood as intended?

SOL recommendation: typing prepares a draft; handing over the return freezes a user-attributed correction instruction; the producer applies it inside its existing mandate and issues a receipt; a shared-spec change goes through the qualified host and Track; selection, ratification and signature stay separately named acts, without adding a confirmation to every already-authorised routine correction. ASTRA recommendation: treat the corrected text as an explicit change request, keep its exact words, apply within the existing mandate, explain every impossibility, return a receipt and the new version; reserve binding approval to its own distinct gesture.

Blocking scope: does not block FE-0–FE-5 (the contract carries corrections without deciding their authority). Blocks the *policy* defaults of FE-6 (when application may proceed without a further explicit act by whom).

### Q2 — What must be directly reworkable for the first increment to be genuinely usable, and what must stay evidence?

Context (both analyses): the real case mixes narrative prose, recommendations, questions, options, lists, tables, a diagram, history, citations and provenance. The model does not define all of these as editable paragraphs; a global editor would risk turning references and evidence into plain rewriteable text. Editing a recommendation on a clickable card also conflicts gesturally with selecting it.

Open question: which concrete corrections must be possible without leaving the dossier for you to consider this first increment really usable, and which information must keep an evidence function rather than become rewriteable text?

SOL recommendation: start with prose/list paragraphs and narrative question/option fields; keep other blocks preserved with an explicit perimeter; extend table cells and the diagram under their own profiles; preserve history and attestations as facts of origin — a request to correct such a fact receives a trace, not a silent rewrite. ASTRA recommendation: start with source-backed narrative fields, with paragraph insertion/merge and bounded rich content; preserve evidence, provenance and IDs; name temporarily non-editable fields in the witness.

Note: D20 operationalises the *technical* half (P0 + evidence-gated list inclusion); the *usability* judgement of that perimeter on your real dossiers remains yours. Blocking scope: final acceptance wording of the first increment (FE-9 stage 2), not its construction.

### Q3 — How should divergent versions and draft continuity be handled across closing, machines and new revisions?

Context (both analyses): offline use makes divergent versions normal. The current kit loses selections on close; browser/`file://` storage offers no universal durability or cross-machine transport guarantee; carrying paragraphs across rebuilds requires transporting their manifest. Rejecting everything at the slightest divergence is fatiguing; a silent merge can change meaning.

Open question: how do you want to resume and share a dossier under correction, how should your corrections be reconciled with a newer version produced meanwhile, and at what level do you want to arbitrate a disagreement yourself?

SOL recommendation: from the start, a complete downloadable/re-importable return including paragraph lineage, with base-bound browser recovery as a supplement; a new revision explicitly reconciles still-applicable corrections and shows conflicts; automatic multi-machine sync only with a later durable host, never simulated by local storage. ASTRA recommendation: auto-rebase unchanged paragraphs whose identity is certain; present baseline/current/requested for conflicts; keep the batch atomic initially and offer an explicit split if useful; preserve the draft until resolution.

Blocking scope: §5.4/§5.5 implement the mechanism neutrally; Q3 governs the *default arbitration UX* (whole-batch hold vs guided split) finalised at FE-5/FE-6.

### Q4 — Who carries the work when the original producer is gone, and what counts as taken in charge?

Context (both analyses): the bus can deposit into an inbox; several agents may work on one repository; a session can end; the producer of a given dossier may be an agent with no Track item, or no longer live. Neither live presence nor project name proves producer identity. The format must stay useful by a copied JSON/YAML file. Continuity also spans three places: the portable file, the producing session, and the sentropic application (which hosts the editor capital but no longer hosts Focus).

Open question: to whom should responsibility for taking up corrections pass when the initial producer is absent or replaced, what proof of takeover suffices for you to consider the return inside the work loop, and which minimum deliverable makes the resumption useful immediately across those three places?

SOL recommendation: correlate to the producer and the original request; keep an explicit designated successor; allow manual file handover; display exported / delivered / processed / applied distinctly, with the affected paragraphs and the new revision; never pick an agent merely for being first live on the repository. ASTRA recommendation: deliver the complete portable loop first under h2a conduct with a generic DS component, manually consumable return included; add live delivery and sentropic adoption afterwards under the same contract; resuming a draft from an explicit file must remain possible on another machine.

Blocking scope: FE-5 manual consumption works under any answer; Q4 governs FE-6 routing/succession policy and the takeover evidence the UI must show.
